# Спецификация production версии Tag Files

Статус: согласованная целевая спецификация от 14 ноября 2026. По D-16 владелец одобрил текущий макет v27 и его пользовательское поведение как baseline production UI: [макет и сценарии](prototype/README.md), [паспорт согласованной версии](prototype/accepted-baseline.json). Таблица F-01…F-38 в [историческом реестре](01-current-behavior.md) задаёт функциональный паритет; [решения D-01…D-16](06-product-questions.md) и контракт ниже задают целевые изменения. Принятый UI, включая selection/bulk replace только в list, обязателен для первого релиза. Отдельный backlog содержит только возможности вне v27 и подтверждённого паритета.

## Назначение и границы

Tag Files — личная локальная медиатека с организацией через теги, ручные коллекции и сохранённые поиски. Один пользователь разворачивает приложение в Docker Desktop на современном Mac и открывает браузер на том же компьютере. Текущую библиотеку из нескольких тысяч записей и примерно 100 GB медиа необходимо перенести с проверкой целостности.

Пользователь работает с медиа-контентом через теги. У материалов нет пользовательских названий; входные имена после загрузки не становятся атрибутом готовой библиотеки. Галерея и просмотр отдают основное место фото/видео и тегам. В обычном состоянии они не показывают технические сведения о файлах, описания, постоянные подсказки, слоганы или метки готовности. Компактные навигация, favorite, изменение тегов/коллекции и media-controls остаются доступны. Помощь открывается по запросу; loading, ошибки и необходимые результаты операций показываются только в соответствующей ситуации. Это подтверждённое правило D-12.

По D-13 язык интерфейса — английский: видимый системный текст, placeholders, tooltips, accessible names, ошибки, empty states и встроенная помощь. Демо-теги, коллекции и сохранённые поиски также английские. Документация остаётся русской; её русские названия сценариев и объяснения не задают текст UI. Переключатель языка/i18n не добавляется. Пользовательские данные поддерживают прежний Unicode и не переводятся при загрузке или миграции.

Уточнение D-12 для миниатюр: media-card и related thumbnail не имеют постоянного ряда тегов. Hover или keyboard focus открывает плавающий popup со всеми тегами обычным неинтерактивным текстом через `·`, без chips, ссылок и `+N`. Обычно popup расположен под миниатюрой; при нехватке места у нижней границы окна он появляется над ней. Он не перестраивает grid, не обрезается контейнером/краями окна, сохраняется при переходе указателя через зазор и закрывается по Escape без переноса focus. Область требования — миниатюры: теги viewer/list сохраняют кликабельность, как и заголовок Same tags для AND-поиска.

По D-14 от 12 ноября 2026 используется один viewer с canonical URL из grid, list и связанных материалов. Медиа занимает основную область сверху; теги, компактные действия и группа коллекции располагаются ниже, без правой информационной панели. Контекст сохранённого поиска принадлежит URL/Back, без дополнительного постоянного label. Прежние quick-preview и отдельная полная карточка объединены с сохранением всех действий. Category остаётся saved query, не назначением item; перенос вторичной информации под контент не добавляет поля и технические сведения.

Первый production-релиз воспроизводит реализованные функции и добавляет необходимую эксплуатационную надёжность. Многопользовательские пространства, роли, SaaS, синхронизация между устройствами, публичные ссылки, AI-разметка, мобильное приложение и облачное хранение находятся за его пределами. Будущие функции не должны требовать замены модели item/tag/collection/asset/job.

Новые загрузки принимают только фото и видео. Пользователь выполняет одну операцию загрузки; подготовка рабочей версии, публикация и очистка временного входа происходят автоматически. Разрешение сохраняется, дополнительного архива оригиналов и корзины нет. Файлами управляет только приложение. Миграция старой библиотеки и резервирование данных выполняются отдельными внешними скриптами; соответствующие handlers, CLI, API, UI и расписания не входят в сервис.

Приложение остаётся modular monolith с SQLite и durable jobs. Развёртывание состоит из двух контейнеров: приложение с SPA/API/FFmpeg и SeaweedFS 4.53 `weed mini` с embedded LevelDB2, без PostgreSQL. До любых загрузок сохраняется и проверяется глобальное правило `fs.configure -locationPrefix=/ -fsync=true -apply`; его конфигурация входит в backup. Storage volume сохраняет весь `/data`, включая `master`, `filerldb2` и `volumes`. S3 endpoint доступен только внутри Docker-сети; browser работает с same-origin API и media proxy приложения, без прямых S3 URL или credentials. Обоснование выбора и ограничения хранилища — в [решении по S3](08-s3-storage-decision.md).

Рекомендуемая реализация для разработки AI-агентами — Go 1.27.4 и статическая React 19.3.1 SPA на Vite 8.3 с TypeScript strict; Node 26 используется только при сборке. Сервер раздаёт собранный клиент, API и медиа с одного origin, без SSR и Node runtime. Выбор стека, его зависимости и проверяемые ограничения описаны в [решении по прикладному стеку](09-application-stack-decision.md) и [целевой архитектуре](03-target-architecture.md). Это техническая рекомендация, которая не меняет D-01…D-16, продуктовую семантику и границу отдельного backlog. Для AI-реализации важны явные контракты, генерация типов и проверки, а не неподтверждённое преимущество агента в конкретном framework.

Компоновка организационных разделов уточнена 14 ноября: `Tags` — компактная таблица `Tag`/`Usage count`, `Categories` — `Name`/`Query`/`Items type`. Имена создают новую галерею: точный tag query либо category query + type, новые первыми и страница 1. Collection link создаёт такой же новый контекст с collectionId; Back из viewer сохраняет порядок и страницу своего origin. `Collections` — компактная auto-fill сетка с минимальной шириной 160 px, квадратной обложкой, именем 14 px под ней и gap 12 px; три коллекции не растягиваются в три огромные панели. Нет описаний, больших зелёных cards или отдельного CTA Open media. Под каждым списком/сеткой находится total числа сущностей этого раздела, не количества их медиа. Модели и production-операции управления сохраняются в объёме F-реестра. В v27 CRUD этих сущностей не реализован; одобрение макета не отменяет создание/rename тегов через имеющиеся API, category CRUD, collection CRUD и существующие UI-входы к этим операциям. Неработающие кнопки в целевом UI недопустимы.

## Термины и совместимость

| Термин | Смысл |
| --- | --- |
| Элемент | Одна запись библиотеки с primary media, метаданными и связями |
| Тег | Независимая метка; у элемента несколько тегов |
| Коллекция | Аналог папки с ручным членством; у элемента не больше одной коллекции. Теги обеспечивают множественную классификацию |
| Категория прототипа | Сохранённая строка tag query и необязательный media type, а не родитель тегов |
| Сохранённый поиск | Смысл категории: query + необязательный тип. Видимый раздел называется `Categories`; прежнее предложение `Saved searches` не используется |
| Primary asset | Единственная основная рабочая версия файла после обработки; у video это MP4, без отдельного сохранённого input |
| Производный файл | Preview/poster, который можно повторно построить из имеющегося primary |
| Загрузка | Путь от browser upload до ready item; завершение передачи байтов ещё не означает успех обработки |
| Миграция | Одноразовый offline-перенос legacy библиотеки внешним скриптом в отдельную новую копию |

Сохраняются результаты валидных текущих запросов, метаданные, ручное членство, счётчики, избранное, доступные legacy файлы и все реализованные операции API, в том числе без доступной кнопки в UI. Старые структуры JSON, имена бакетов и пути файлов сохранять не требуется. Прежние числовые item ID и переход `/content/:id` сохраняются для существующих закладок; специальный adapter старого S3/API не входит в baseline.

Технические ограничения старого Angular-прототипа не становятся требованиями: скрытый лимит 300, недоступный пункт Favorites, игнорирование неизвестных символов parser, потеря состояния при refresh и исчезновение failed jobs не должны воспроизводиться. Любое намеренное изменение продуктовой семантики сверяется с владельцем продукта.

## Пользовательские сценарии и ожидаемые результаты

| ID | Сценарий | Контракт результата |
| --- | --- | --- |
| S-01 | Загрузить несколько файлов, при желании в коллекцию | У каждого свой upload ID; pending/error доступны после закрытия диалога. Ready/cancel исчезают немедленно, готовый item остаётся в библиотеке |
| S-02 | Найти элементы по тегам, типу и сортировке | Полная доступная выдача с total, пагинацией и воспроизводимым URL; сохраняются grid/list и настройки плотности |
| S-03 | Просмотреть изображение либо видео | Один viewer из grid/list/related, медиа сверху и теги/коллекция ниже; zoom/rotate изображения и video controls доступны; stream не загружается целиком заранее |
| S-04 | Перейти prev/next и вернуться к выдаче | Сохраняются запрос, порядок, место в списке и origin; после refresh контекст восстанавливается либо объясняется его истечение |
| S-05 | Изменить теги и коллекцию одного материала либо выделенных строк list | Черновик не изменяет библиотеку до Save; оба поля и весь выбранный набор фиксируются одной атомарной командой; grid без selection |
| S-06 | Отметить избранное и учесть просмотр | Флаг и счётчики сохраняются; повтор HTTP-запроса не отменяет флаг и не удваивает один view event |
| S-07 | Управлять тегами | Сохраняются чтение, создание, переименование и статистика; удаление тега — предлагаемое расширение |
| S-08 | Создать категорию в форме и открыть позже; shortcut из поиска — предлагаемое расширение | Query/type сохраняются; результат отражает актуальную библиотеку |
| S-09 | Управлять коллекцией | Создание, переименование, просмотр, назначение элементов и удаление группы с сохранением файлов |
| S-10 | Найти похожие | Строго тот же непустой набор тегов, исключая текущий item; новые первыми |
| S-11 | Удалить элемент | Явная команда удаляет его окончательно, без корзины; очистка имеет наблюдаемый результат и retry. UI-вход и подтверждение — отдельное UX-предложение |
| S-12 | Перезапустить контейнеры и продолжить | Метаданные, подтверждённые S3 parts и результаты сохранены; незаконченные jobs восстанавливаются без дубликатов |
| S-13 | Перенести библиотеку, сделать backup и restore внешними скриптами | Остановленное приложение, а для cold backup/restore также gateway; отдельный tool и manifest доказывают полноту, в приложении этих операций нет |

S-01…S-11 обобщают существующие функции с явно названными расширениями. Атомарная форма, восстанавливаемая навигация, идемпотентность и S-12 — технические требования к production-надежности. S-13 — внешний операционный сценарий, не функциональность сервиса. Редактирования description и публичного удаления тега сейчас нет; хранение их данных и создание тегов через API уже есть. Функциональная трассировка к исходникам остаётся в реестре F, а не заменяется этой укрупнённой таблицей.

## Метаданные и операции

Совместимая основа: описание nullable до 150 символов; tag name 1…50, буквы/цифры/дефис; названия категории и коллекции 1…200. Эти ограничения остаются текущими defaults. Unicode сохраняется. У item нет `title`, `displayName` или `originalFilename`: в текущей модели `FileName` — служебный object key, а не название медиа. Входное имя используется только в pending/error upload session; при ready/cancel session с именем удаляется, в готовый item оно не копируется. Сохранившиеся исторические имена остаются во внешнем migration archive вместе с исходными записями, без создания новой пользовательской модели имён. Сервер возвращает field errors до сохранения формы.

Назначение тегов в прототипе заменяет весь набор. В v1 операция `replace` сохраняется явно; `add`/`remove` — отдельные предлагаемые режимы bulk editor, не неявное изменение существующей операции. Assign collection задаёт одну коллекцию либо NULL. Пакет проверяет существование всех элементов и тегов до изменения; нет частичного обновления успешно найденных ID. Форма item объединяет tags/collection в одну транзакцию; description хранится и читается через API, но не занимает место в viewer/editor. Его редактор — отдельное расширение.

Редактор рассчитан на типичные 20–30 тегов и несколько сотен коллекций; 30/350 — приёмочный пример, не жёсткие лимиты. Теги представлены выбранными chips и полем поиска: локальное case-insensitive вхождение подстроки в существующие имена, уже выбранные ID исключены. Коллекция — одно searchable single-select поле с именем выбранной коллекции, chevron и inline clear для nullable `No collection`; отдельного chip и второго поля ввода нет. Выбор коллекции заменяет прежний ID, а не добавляет ещё один. Ввод query сам ничего не назначает и не создаёт; выбор option/удаление tag chip/clear меняют только draft по ID. ArrowUp/Down перемещают активную option, Enter подтверждает выбор; в tag search Enter без активной option либо запятая могут подтвердить только совпавшее существующее имя из локальных подсказок. Неизвестное имя не создаётся, Enter в поисковом поле не выполняет Save. Escape закрывает popup, Tab переводит focus без неявного выбора. При Escape, Tab или blur неподтверждённый query коллекции заменяется label выбранного draft ID либо `No collection`. Cancel ничего не сохраняет; failed Save сохраняет draft и ввод тегов, label коллекции соответствует подтверждённому draft ID. Pending Save блокирует поля, chips, повтор Save и закрытие формы до определённого исхода. До Save кнопки Cancel/Close, backdrop и Escape при закрытом popup отклоняют draft без изменения metadata; focus возвращается к исходному действию. Case-insensitive поиск подсказок не меняет binary/case-sensitive серверный tag query и идентичность тегов, не нормализует имена и не добавляет tag autocreate.

Внешний responsive bounding box редактора стабилен при focus, вводе, очистке и выборе, независимо от 0 или 350 результатов; высота окна не определяется выпадающим списком. Оба popup расположены поверх формы вне потока layout, имеют собственную прокрутку и максимальную высоту 220px с ограничением доступной высотой viewport; при необходимости открываются выше поля. Они не обрезаются overflow диалога. Прокрутка результатов не прокручивает вложенную форму/страницу; при нехватке места прокручивается тело формы с chips и полями, а header/footer не меняют положение. Footer с Cancel/Save остаётся доступен и в невысоком окне.

На странице Collections поле `Search collections` фильтрует полный справочник на frontend по буквальному case-insensitive вхождению подстроки, live при вводе. Есть clear и no-match state; компактная сетка сохраняется. Footer показывает найденное число/общее число коллекций, а не media count. Фильтр хранится в URL (в макете `#/collections?search=…`) и восстанавливается при Back/reload. Для масштаба около 350 коллекций отдельные API search/pagination не добавляются: GET collections возвращает весь справочник до клиентской фильтрации; пагинация материалов внутри коллекции остаётся прежней.

Сравнение имени тега сохраняется ordinal case-sensitive без изменения регистра и скрытой Unicode-нормализации. Одинаковые имена, как сейчас, допускаются; новый UNIQUE(name) и автоматическое слияние не добавляются. Связи и новые API-операции используют tag ID, чтобы однозначно выбрать запись. В текстовом поиске имя означает OR всех совпадающих ID; старые одноимённые теги мигрируются раздельно.

Saved search хранит стабильные ссылки на tag ID, актуальную строку queryText и parser version. Rename тега в одной транзакции обновляет его имя и queryText зависимых категорий, сохраняя AST, NOT/AND/OR и набор результатов на неизменной библиотеке. Исторический legacy source хранится отдельно. Удаление тегов не входит в baseline API; возможное расширение должно определить зависимости сохранённых фильтров. Удаление коллекции освобождает элементы, не удаляя их. Автоматическая обложка остаётся thumbnail самого старого элемента с tie-breaker id ascending. Выбор первой готовой preview, ручная cover и порядок элементов — отдельный backlog.

Применение saved search выполняется по `savedSearchId`, а не повторным разбором старой строки. URL выдачи и navigation context сохраняют этот ID; фильтр берётся из AST и media kind записи. `q`/`kind` и `savedSearchId` взаимоисключающие источники фильтра. Sort/page/seed остаются внешними параметрами. Пользовательское изменение фильтра переводит выдачу в ad-hoc query явно, не меняет сохранённый поиск.

Saved-search GET возвращает `queryText` (актуальное выражение с текущими именами), `legacySourceText?` (неизменённый исходник миграции), `queryAst`, `displayTerms[{tagId?,currentName,sourceName?}]`, `parserVersion`, `validationState`, `mediaKind`, `version`. UI строит читаемый expression из AST/текущих имён, при неоднозначности показывает ID/предупреждение. PATCH только name не трогает AST; PATCH с новым queryText явно перекомпилирует всё выражение по текущим именам, валидирует его и возвращает разрешённые term. Текстовый editor не должен отправлять старую строку, если пользователь менял лишь название. В сложной legacy неоднозначности можно сохранить прежний AST и изменить только name; явное текстовое редактирование сообщает о перепривязке.

«Похожие» сохраняет точное равенство непустых наборов tag ID, исключает текущий item и показывает новые первыми. Другие типы медиа и элементы из других коллекций допускаются. В viewer сначала идёт группа коллекции: heading — только имя-ссылка, без дубликата у тегов, In collection и отдельного All; при назначенной коллекции heading остаётся даже без siblings, при NULL группы нет. Следующая related-секция Same tags содержит exact-set результат; её кликабельный heading открывает обычную AND-галерею по всем именам тегов, UploadedDesc/page 1, без type/collection/subset. Эта галерея включает текущий item и материалы с дополнительными тегами и потому не равна related exact-set. Расширенное сходство по пересечению, embedding или картинке не входит в parity.

## Язык поиска

Грамматика production v1 расширяет распознавание букв до набора, разрешённого tag names, и явно проверяет ввод. Совместимость всех валидных legacy ASCII-запросов обязательна.

```ebnf
query      = or_expr | empty ;
or_expr    = and_expr, { "||", and_expr } ;
and_expr   = term, { "&&", term } ;
term       = [ "!" ], tag | "(", or_expr, ")" ;
tag        = letter_or_digit_or_hyphen, { letter_or_digit_or_hyphen } ;
```

Пробелы вокруг операторов и скобок не значимы. Приоритет: `!tag`, затем `&&`, затем `||`; скобки меняют порядок. Неявного AND, кавычек, `NOT`/`AND` словами и `!(...)` в совместимой грамматике нет. Их добавление требует parser version и отдельных примеров; ошибка не превращается в другую выборку. Предлагаемые пределы: 4 096 символов запроса, 256 term, вложенность до 32; превышение даёт 422 с указанием места.

| Пример | Результат |
| --- | --- |
| пустой query | Все ready элементы, затем применяется media type |
| `cat` | Элементы с тегом `cat` |
| `cat && dog` | Оба тега |
| `cat \|\| dog` | Любой из двух |
| `cat && !dog` | Есть `cat`, нет `dog` |
| `(cat \|\| dog) && !portrait` | Группа OR и исключение |
| `unknown-name` | Пустая выборка, если такого имени нет |
| `!unknown-name` | Все ready элементы, если такого имени нет |
| `cat dog`, `cat & dog`, `cat &&` | Понятная ошибка синтаксиса, без выполнения изменённого запроса |

Имя сопоставляется точно, включая регистр. Если имя неоднозначно, оно означает OR всех совпадающих tag ID; UI сообщает о неоднозначности при редактировании. Для saved search отсутствующий term остаётся unresolved именем и может начать соответствовать новому тегу с таким именем; это сохраняет динамический смысл legacy строки. Уже разрешённые ссылки остаются ID при rename, а актуальный queryText пересобирается. Эта техническая модель реализует подтверждённое правило переименования и сохраняет текущую семантику имён.

При создании нового тега соответствующие ID-группы категорий расширяются всеми текущими тегами совпадающего имени, включая разрешение ранее unresolved term. Для категории `cat` создание второго `cat` и назначение его новому item включает этот item в результат, как в старом строковом фильтре. Create и обновление зависимостей атомарны. Rename выполняет D-07 без повторного разрешения других неизвестных имён; например, переименование связанного `a` в ранее отсутствовавший `x` не должно одновременно менять смысл отдельного unresolved `!x`. Для сложных совпадений UI показывает привязанные ID через displayTerms; AST остаётся источником выполнения, а явная правка текста заново разрешает имена.

Тип: all, Unknown, Text, Image, Video, Audio в API, как в текущем enum. Text/Audio сохраняются при миграции и фильтрации, но это не обещает новый viewer этих форматов. По D-13 UI сохраняет два независимых icon-toggle Image/Video и их boolean state: `10` → Image, `01` → Video, `00` и `11` → all. Нельзя сводить два последних состояния к одной отмеченной кнопке или заменять controls единым select. Выбор, Clear, применение saved search и возврат из viewer согласуются с текущей семантикой и восстановлением URL-контекста; Clear снимает оба toggle. В согласованном UI переход по коллекции открывает ту же галерею в области collectionId; query и media kind пересекаются с её членством, URL/Back сохраняют эту область. Это часть v27, а не будущий фильтр. Clear дополнительно снимает collection scope и временное подмножество результатов. Полнотекстовый поиск по filename/description и отдельная фильтрация Favorites остаются вне baseline.

Сортировки сохраняются все: `UploadedDesc`, `UploadedAsc`, `VideoDurationDesc`, `VideoDurationAsc`, `ViewCountDesc`, `ViewCountAsc`, `Random`. При равных значениях применяется стабильный tie-breaker по ID. NULL duration, как сейчас, при ASC идёт впереди, при DESC в конце. Новый поиск или refresh создаёт новый Random порядок; страницы и prev/next внутри одной выдачи удерживают его через технический контекст. Это не вводит обязательную кнопку «Перемешать» вместо текущего поведения.

Сортировка открывается icon-trigger и показывает семь пунктов с иконками и подписями `Uploaded ↓`, `Uploaded ↑`, `Duration ↓`, `Duration ↑`, `Views ↓`, `Views ↑`, `Random`. Выбранный пункт отмечен; trigger не превращается в постоянно видимый select. Add/Choose files доступны только в `Uploads`, куда ведёт sidebar; в галерее нет Add/upload shortcut и control `?` для справки поиска. Иконка добавления в Uploads сохраняет английские accessible name/tooltip. Все controls работают с клавиатуры, сохраняют focus/pressed/expanded semantics; скрытие постоянной подписи не означает отсутствие доступного имени.

В одной рамке search form находятся поле запроса и icon-controls Photos, Videos, Sort, Clear filters. Clear filters виден всегда, сбрасывает query/type, collection scope, временное подмножество и страницу к 1, сохраняя sort и grid/list. Размеры `+`/`−` и Grid/List расположены справа снаружи search form, на одной строке desktop; в макете кнопки единообразны, 32 px, с одной семьёй иконок. На узкой ширине разрешён перенос групп без горизонтального overflow. Общее число совпадений `totalItems` находится в footer под grid/list рядом с пагинацией, не в header: это весь результат активного поиска, а не 24 элемента текущей страницы.

Статистика тегов по умолчанию глобальная, как в прототипе: все имена, включая неиспользуемые с нулём, `usageCount DESC, tagName ASC`. Одноимённые legacy теги объединяются для совместимого представления статистики; отдельное представление по ID может быть добавлено для разбора дублей. Предлагаемые facets текущего query/type — отдельный `scope=search`, до пагинации, и явно обозначенное расширение; нельзя заменить ими глобальную страницу Tags. Для facets считать distinct item ID, чтобы одинаковые имена не удваивали результат. Total и выдача используют один фильтр.

## Загрузка и медиаполитика

Новые загрузки ограничены фото и видео. MIME браузера не определяет доверенный тип: probe и allowlisted decoder проверяют содержимое. Неподдерживаемый вход получает 422 `unsupported_media_type` или `unsupported_codec`, не создавая ready item. Исторические Unknown/Text/Audio переносятся без потери байтов и метаданных, остаются доступны для скачивания. Общее `video/*` не является обещанием декодировать любой возможный codec; fixture matrix проверяет текущие поддерживаемые сценарии и ясную ошибку для остальных.

Для новых загрузок сохраняется одна рабочая версия primary и preview. Отдельных архивных originals и второй playback-копии нет. Видео использует текущий выходной профиль MP4 H.264/AAC с faststart; фото следует текущему подходу, при котором уже пригодный формат может пройти без перекодирования. Если преобразование фото требуется, сохраняется только результат. Размер основного кадра, пропорции и ориентация сохраняются; preview может быть уменьшено. Параметры кодирования берутся из текущего поведения, без обещания улучшить качество входа или обязательной новой ручной настройки.

Пользователь просто загружает файл: обработка, проверка и публикация результата выполняются автоматически, без подтверждения конвертации или отдельного выбора хранения input. После **каждого успешного ответа** CompleteMultipartUpload приложение проверяет incoming через HEAD и полный GET/hash: HTTP 200 сам по себе не доказывает наличие собранного объекта. Только проверенный `incoming/<library-id>/<upload-id>/source` с ожидаемым размером, согласованным manifest и сохранённым полным SHA-256 переводится в queued processing. Вход остаётся там до подтверждённого PUT канонического primary, полного GET с проверкой размера/SHA-256 и SQLite ready commit item с upload_id, удалением session/parts/ingestion job и самостоятельным cleanup intent. Локальный scratch для probe/conversion не является единственным сохранным входом. Ошибка до `ready` сохраняет необходимый вход для retry и не считается успешной публикацией. После `ready` durable cleanup job удаляет incoming; ошибка этой очистки оставляет наблюдаемый cleanup pending/retry, **сохраняет ready primary, не возвращает строку в Uploads** и не создаёт повторный импорт. Poster failure тоже не уничтожает готовый primary. Старые видео migration script копирует как есть, без массового перекодирования и восстановления отсутствующего исходника.

Технические требования к upload: pending/error batch/file projection, streaming, безопасный повтор и независимая очистка после ready/cancel без TTL незавершённой работы. Передача использует нативный S3 multipart через streaming proxy приложения: browser считает SHA-256 каждой части и отправляет digest в header `X-Part-SHA256` (base64 от 32 байт) вместе с streaming body; приложение потоком вызывает UploadPart без буферизации файла целиком. Сервер выбирает `partSize` по объявленному размеру файла: не более 10 000 parts, каждая от 5 MiB до 5 GiB, кроме последней, которая может быть меньше 5 MiB; небольшой файл также передаётся одной частью. Повторная запись part number допустима только теми же байтами с прежними digest и размером; другое содержимое получает 409 и требует новой session. Отдельные UI pause/resume controls не обязательны для паритета. Defaults: max file 20 GiB, параллельных передач 2, один FFmpeg job; ограничения настраиваются и проверяются на fixtures. Старые 100 GB переносятся внешним скриптом, не единым browser request.

Клиент считает хеши в Web Worker и ограничивает число и размер одновременно находящихся в памяти частей. Для Safari-совместимого byte progress отдельный binary transport передаёт `Blob`-части через XHR; JSON-клиент не сериализует их и не читает весь файл в RAM. Полный content fingerprint вычисляется инкрементально ограниченными порциями: `SubtleCrypto.digest` не принимает поток, поэтому вызов для полного `file.arrayBuffer()` не является допустимой реализацией для 20 GiB. Эти механизмы поддерживают существующий upload/recovery-контракт, не добавляя обязательных кнопок pause/resume или фоновой передачи после закрытия браузера.

По D-15 от 14 ноября Uploads содержит только pending/error и не является историей загрузок. Receiving/idle, ошибки и их необходимые durable inputs не протухают: без expires_at, expiry-driven abort и ограничения X дней. Ошибка остаётся до успешного retry или ручного cancel. Успех — проверенный primary + SQLite ready commit; в той же транзакции создаётся item с nullable UNIQUE upload_id (legacy NULL), убираются session/parts/завершённый ingestion job и сохраняется независимый cleanup intent. Строка сразу исчезает из Uploads; cleanup incoming/scratch и poster work выполняются отдельно и не удерживают её. При cancel fence и самостоятельный cleanup receipt фиксируются атомарно с удалением строки; необходимые working records живут до завершения Abort/Delete/process/in-flight reconcile. Гонку выигрывает либо ready, либо cancel: cancel не удаляет уже опубликованный item. Возраст не запускает удаление; request timeouts, leases и retry delays остаются механизмами исполнения. Отдельных history-таблицы, подтверждения ознакомления или archive batch нет.

В bucket `tag-files` канонические immutable assets получают уникальные ключи `primary/<library-id>/<asset-id>/media.ext` и `previews/<library-id>/<asset-id>/<profile>/poster.jpg`; имя пользователя не становится ключом. **До PUT** SQLite сохраняет candidate asset ID/key, publication attempt/lease generation и expected SHA-256/size результата. Повтор того же candidate разрешён только теми же байтами: иная conversion или новая lease получает новый candidate/key. При потерянном ответе PUT та же попытка сначала выполняет полный GET/hash своего candidate и при совпадении переиспользует его; mismatch не перезаписывается. Commit `ready` проверяет актуальные generation/lease. Lease не останавливает уже принятый storage-запрос, поэтому безопасность обеспечивают неизменность байтов одного candidate и разные ключи разных попыток. Содержимое готового ключа не перезаписывается, а cleanup удаляет только известные неиспользуемые candidates. SQLite хранит объектные references, размеры, полный SHA-256, состояния sessions/jobs и служит источником истины для pipeline; S3 notifications не запускают обработку. ETag — непрозрачный токен S3 для части или объекта, а multipart/composite checksum не считается полным SHA-256 файла.

Для image thumbnail сохраняется функция preview, для video — poster и duration. Точные 300 px и 10% duration из прототипа не являются незаменимым UI контрактом; профиль должен обеспечивать достаточную резкость для целевой сетки, корректный aspect ratio и ориентацию. Новый профиль версионируется и может пересоздаваться без потери primary.

## Избранное и просмотры

Хранится флаг favorite у любого item. Новый HTTP контракт устанавливает значение `true/false`, сохраняя результат повторного запроса. Отдельная страница «Избранное» — предложенное завершение существующей модели, а не подтверждённая работающая страница прототипа.

View count в едином viewer по D-14 сохраняет правило трёх секунд: уход раньше отменяет отправку. Legacy view count и lastView переносятся точно. Условие видимости вкладки или фактического playback не добавляется; миниатюры, grid/list и чтение API сами по себе не учитываются. Разделения quick-preview/detail больше нет. Повтор того же event ID не увеличивает число, новое открытие создаёт новое событие. Retention event ID — техническая настройка, достаточная для повторов HTTP, а не новое правило подсчёта.

В React повтор effect при StrictMode и сетевой retry одного открытия используют тот же event ID; cleanup отменяет таймер при уходе. Чтение detail через GET и query-cache refetch само по себе не создаёт view event. Проверка StrictMode не меняет правило трёх секунд и не отключает серверную идемпотентность.

## HTTP API новой версии

Контракт ниже задаёт операции, а не копию старых маршрутов. JSON использует camelCase, enum передаются строками. Item summary содержит `id`, `mediaKind`, `description`, `uploadedAt`, `tags[{id,name}]`, `collectionId`, `isFavorite`, `viewCount`, `lastViewAt`, `durationSeconds`, `posterUrl?`, `contentUrl?`, `processingState`, `version`. Поля пользовательского названия и исходного имени не добавляются. Сохранение description, timestamps, счётчиков и состояния в API не требует их показа в галерее/viewer; технические поля обслуживают сортировку, операции и совместимость. Физические пути и секреты storage в DTO отсутствуют.

Источником HTTP-контракта служит versioned OpenAPI 3.0.3: из него генерируются JSON-типы и handlers через `oapi-codegen`, TypeScript-типы через `openapi-typescript`, клиент использует `openapi-fetch`. Генерация и её diff проверяются при изменении схемы. Binary upload и GET/HEAD/Range обслуживаются отдельными потоковыми Go `net/http` handlers: JSON binding/middleware не буферизует их body. Способ генерации не добавляет полей и не меняет описанную ниже семантику операций; технические подробности — в [решении по стеку](09-application-stack-decision.md).

| `POST /api/v1/upload-sessions` | Batch/files с clientFileId, filename, size, collectionId?, content fingerprint при наличии; session ID, серверные partSize/partCount/limits и generation по уникальному file ID, не filename |
| `PUT /api/v1/upload-sessions/{id}/parts/{number}` | Generation, размер, `X-Part-SHA256` и streaming body; durable part binding до proxy к UploadPart с проверяемой SHA256 checksum; ETag непрозрачен; другие digest/size того же номера → 409 |
| `GET /api/v1/upload-sessions/{id}` | Для pending/error: state/generation, limits, bindings и ListParts. После ready session удалена, lookup items.upload_id возвращает success/itemId; иначе неизвестный upload, без создания новой session |
| `POST /api/v1/upload-sessions/{id}/complete` | Generation и ordered partNumber/ETag; CAS receiving→completing, drain известных writers и проверка manifest; CompleteMultipartUpload + incoming HEAD/полный GET/hash после каждого успеха; pending operation до проверки, затем 202 с тем же job ID; после ready повтор находит success/itemId по items.upload_id без session/history |
| `DELETE /api/v1/upload-sessions/{id}` | Fence + немедленное удаление pending/error строки; независимый receipt доводит Abort/HEAD/Delete/reconcile. Ready item не удаляется: если ready победил гонку, возвращается его существующий исход |
| `GET /api/v1/upload-batches` | Только текущая pending/error проекция sessions по batch_id и progress; ready/cancelled отсутствуют, batch без оставшихся задач исчезает; отдельной history-таблицы нет |
| `POST /api/v1/jobs/{id}/retry`, `POST .../cancel` | Явное действие и наблюдаемый результат |
| `GET /api/v1/operations/{id}` | Pending/completed/failed, исходный HTTP status и resource/result; неизвестный либо истёкший ключ — 404 |
| `GET, HEAD /media/{assetId}` | Same-origin proxy к S3, streaming, Range/conditional headers; role primary или poster; архивных originals нет |
| `GET /api/v1/system/status` | Versions, queue, disk и состояние текущей библиотеки; показателей бэкапа нет |
| `GET /health/live`, `GET /health/ready` | Процесс жив; SQLite/S3, сохранённое global fsync rule проверено operational preflight, миграции/recovery готовы |

Multipart contract закрепляет неизменяемую привязку **`(session, partNumber, expectedSize, SHA256)` в SQLite до forwarding body**. Размер определяется session/partSize и положением части, digest — header браузера; повтор обязан совпасть с обоими полями. CreateMultipartUpload выбирает SHA256 checksum, а app передаёт ожидаемый digest в S3 UploadPart: storage **обязан реально проверить body**, отвергнуть mismatch и вернуть проверяемую checksum части через ListParts. Это conformance gate закреплённых SDK/storage, который нельзя обойти отключением checksum. ETag остаётся непрозрачным токеном для Complete, не доказательством идентичности байтов. После ambiguous timeout UploadPart клиент запрашивает GET session/ListParts и повторяет только прежние связанные байты.

Complete атомарно делает app CAS `receiving → completing`, закрывает приём новых writers и дожидается известных in-flight отправок. Затем сверяет ListParts с доказанными part bindings, ожидаемыми размерами/SHA256 и суммарным размером и сохраняет ordered partNumber/ETag manifest до S3 Complete. Lease/generation **не прерывает запрос, уже принятый storage**; после restart поздний UploadPart безопасен по содержимому только потому, что для данного номера разрешены те же проверяемые байты. Ответ `InvalidPart` не разрешает слепо заменить сохранённый manifest текущими ETag: reconcile может принять только части с доказанной исходной binding, иначе остаётся явная ошибка. После каждого успешного Complete, включая повтор/reconcile, обязательны incoming HEAD и полный GET/hash до queued/job commit.

При потерянном Create/Complete-ответе reconcile сопоставляет SQLite intent, S3 upload/object и authoritative ListParts; неизвестный исход не превращается в слепое создание второго импорта. Cancel/delete сохраняет durable receipt и fence, который запрещает queued/ready commit. Cleanup повторяет AbortMultipartUpload и HEAD/Delete incoming: late Complete может создать объект уже после первой удачной очистки, и receipt остаётся до завершения reconciliation. Поздний результат не возвращает отменённую загрузку или удалённый item. Сиротские MPU abort допускается только при доказанном владении session; неизвестные keys не удаляются GC автоматически.

После refresh/restore browser File handle не обещается восстановить. Повторно выбранный файл может продолжить существующую session **только после совпадения контентного fingerprint** с исходным; filename, size и clientFileId недостаточны. Если исходный fingerprint отсутствует или не совпал, старые parts не переиспользуются: пользователь явно отправляет файл заново в новой session. Остальные recovery details заданы в [архитектуре](03-target-architecture.md) и [решении по S3](08-s3-storage-decision.md).

Явный запуск обработки F-32 сохраняется через `POST upload-sessions/{id}/complete`: API-клиент может зарегистрировать сессию, передать файл и самостоятельно запустить pipeline, не дожидаясь браузера или события хранилища. Это обычная загрузка новых фото/видео, а не средство переноса legacy. Одноразовый migration script читает старые БД/объекты и создаёт новую библиотеку при остановленном сервисе, без вызовов этого API. Произвольный файловый путь от HTTP-клиента не принимается; старое имя temporary S3-объекта заменяется на session ID.

Настройки F-33 сохраняются в localStorage: grid/list, открытость sidebar и плотность сетки с семью уровнями. Количество столбцов адаптируется к окну вместо жёсткого сохранения 10…4; все уровни различаются видимым размером карточки. Clear поиска снимает query/type/collection/subset, возвращает page 1 и сохраняет sort/view. По D-16 клик имени тега, категории или коллекции из организационных разделов либо viewer/list создаёт новый context: UploadedDesc, page 1, текущий grid/list; tag link снимает прежние type/collection/subset, category применяет свой query + type, collection задаёт только своё членство. Это намеренное изменение прежнего Angular-перехода с сохранением sort. Back из viewer по-прежнему восстанавливает sort/page исходной выдачи.

Sidebar по умолчанию раскрыт и управляется вручную через Expand/Collapse sidebar, без CSS-автосворачивания по ширине. В свёрнутом состоянии остаётся rail шириной `72px`: доступные ссылки-иконки `Library`, `Collections`, `Tags`, `Categories` сверху и `Uploads` внизу viewport. Подписи и бренд скрыты, английские title/aria-label остаются; активный route обозначен визуально и через aria-current. Uploads badge компактен на иконке и продолжает обновляться. Preference сохраняется в браузере. Sidebar sticky, высота `100dvh`; toggle всегда доступен сверху слева вне aside, с `aria-expanded`/`aria-controls`, бренд рядом при раскрытии. Collapse освобождает дополнительную ширину контенту без новой header-строки и без пересоздания workspace, сброса viewer/playback, ввода или list selection. В макете canonical route — `#/categories`, `#/saved-searches` остаётся совместимым alias; document title — Categories. UI-название не переименовывает модель saved query или API `/saved-searches`.

Размер миниатюр меняется только в grid двумя icon-controls `+`/`−`, как в legacy: `+` увеличивает медиа и уменьшает число колонок, `−` уменьшает медиа и увеличивает число колонок. Семь уровней сохраняются, граничная кнопка disabled; slider отсутствует, в list эти controls не показываются. Согласованные по D-16 selection/bulk UI обязательны только в list: grid не содержит checkbox, выбора и bulk-toolbar. Selection ограничен видимыми строками текущей страницы; после изменения фильтра/страницы/view и успешного Save очищается. Toolbar показывает Selected: N, Tags and collection и Clear selection. Bulk editor начинает с пустого набора тегов и No collection, явно сообщает Replaces tags and collection for N items; Save полностью заменяет оба поля у всех выбранных items одной атомарной командой. Это не add/remove и не выбор всех совпадений через страницы; прежние отдельные bulk API сохраняются.

В list четыре колонки: `Media`, `Tags`, `Collection`, `Actions`. Правая Actions-ячейка содержит icon `Edit media`, затем checkbox у самого правого края. Controls появляются по hover/focus-within строки; отмеченный checkbox остаётся видимым и после ухода указателя. Место зарезервировано без reflow; скрытие opacity не удаляет controls из Tab-порядка, keyboard focus делает их видимыми. Edit media открывает существующий single-item editor прямо из списка без viewer и смены route; Cancel сохраняет данные и возвращает focus к Edit media. После Save focus возвращается к Edit media той же строки; если материал перестал соответствовать поиску, focus переходит к полю запроса. Selection/bulk остаются только в list.

Режим списка сохраняется как компактное представление медиа с тегами и доступом к коллекции/Edit; filename/title, размеры, байты, MIME, timestamps и прочая техническая таблица в нём не показываются. Длительность видео допустима как часть media-controls. Скрытие прежней колонки даты по D-12 не меняет сортировку, хранящиеся timestamps или API. Из grid, list и related изображение/видео открывается в одном viewer по canonical URL; отдельного quick-preview нет. Back возвращает исходные query, оба type-toggle, sort, страницу и scroll, prev/next использует текущий navigation context. В viewer сохраняются Space play/pause, Right +5 секунд, Left −3 секунды, Up/Down ±0,1 громкости; сочетания действуют только при фокусе в player context. У изображения ArrowLeft/Right переключают элементы текущего контекста. В формах и диалогах эти действия не перехватывают ввод.

Общие ошибки: Problem Details с `status`, устойчивым `code`, `traceId`, `fieldErrors?`, `position?`, `dependencies?`. 400 — повреждённая форма запроса; 404 — неизвестный ресурс; 409 — конфликт session generation/state/parts/dependency; 412 — устаревшая версия; 413 — размер; 422 — проверяемое предметное/синтаксическое ограничение; 507 — недостаточно диска. Media proxy сохраняет корректную семантику Range, включая 416 и Content-Range для неудовлетворимого диапазона. При неизвестном исходе операции UI проверяет operation/result ID, не повторяет неидемпотентную команду вслепую.

Все создающие POST (tags, collections, saved searches, upload batch, navigation context), bulk и job actions требуют UUID в `Idempotency-Key`; `operationId` результата равен этому ключу. Одинаковые ключ, маршрут и тело возвращают прежний результат; другой request hash с тем же ключом → 409. Результат и предметная запись в SQLite фиксируются одной транзакцией; внешние S3-вызовы согласуются через durable intent/reconcile, без общей транзакции SQLite+S3. Pending возвращает 202 и ссылку на operation; результат доступен через повтор запроса либо GET operations. Ключи и результаты хранятся 7 дней; после этого клиент не делает автоматический create replay. Upload complete дополнительно идемпотентен по upload ID: пока session есть — её state/job, после ready — UNIQUE items.upload_id, независимо от срока operation key; отсутствие обоих не создаёт session заново; view event — по eventId. Если забытый ключ уже неизвестен, UI объясняет неопределённость и проверяет ресурс/session, не создаёт второй объект молча.

Для edit/delete используются If-Match и транзакция. У bulk commands предусмотреть versions либо явное предупреждение об обновлении старого выбора; рекомендуемое v1 — список `(id,version)` и atomic 412 при конфликте. GET не меняет бизнес-данные. Upload batches можно опрашивать раз в 2 секунды во время исполнения: завершённые и отменённые исчезают немедленно, ошибки остаются без TTL до retry/cancel. Пустой batch отсутствует; после прекращения исполнения polling останавливается, при retry возобновляется. Общий 7-дневный operation_results защищает HTTP-повторы и не является историей/retention Uploads. SSE может быть добавлен позднее без изменения модели результата.

## Критерии совместимости и неопределённости

Одобренный v27 фиксирует композицию, английский текст и взаимодействия, а не реализацию на автономном JavaScript. Его localStorage для mock metadata, таймеры Upload/Save, demo batch, debug API, синтетические media и упрощённый parser/Random не заменяют SQLite/S3, предметную grammar и recovery-контракты. Дополнительные допуски демонстрационного parser и фиксированный fallback seed не становятся новыми поисковыми функциями; production grammar и правило нового Random порядка при новом поиске/refresh остаются описанными выше. Отсутствующие в макете upload collection assignment, CRUD, legacy-файлы и API-only операции реализуются по F-реестру и спецификации; их экранные детали не считаются проверенными v27.

Релиз не теряет ни одну строку F-реестра: доступные UI workflows проверяются браузером, API-only — контрактными сценариями. Нет требования воспроизводить внутреннюю последовательность старых endpoint вызовов. Unknown files, legacy names, пустые категории/коллекции и одинаковые timestamps участвуют в приёмке наравне с обычными медиа.

Для legacy категории, которую нельзя однозначно разобрать, отдельный скрипт сохраняет name/raw query/type и исходные данные, помечает её `needs_review` и включает в отчёт. Она не включается молча в «успешно воспроизведённые категории». Переход блокируется при потере данных/функций или исключениях, которые владелец ещё не принял. Явно перечисленное и принятое владельцем исключение допускает переход с указанным ограничением; общий процент скопированных файлов не заменяет это решение.

[Принятые решения](06-product-questions.md) закрывают концептуальные развилки. Остальные детали берутся из текущего поведения. Операционные preflight-проверки и точечные исключения найденных данных выполняются внешним migration script; новых ответов на первоначальный список P0 не требуется. Изменения подтверждённой модели в дальнейшем обновляют спецификацию, архитектуру и acceptance fixtures совместно.
