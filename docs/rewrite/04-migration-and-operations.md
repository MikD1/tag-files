# Данные, миграция и эксплуатация

Документ основан на исходниках репозитория, а не на содержимом рабочей БД или MinIO. Реальные файлы из `data/`, контейнеры и медиа не открывались и не изменялись. Несколько тысяч записей и около 100 GB медиа — исходные условия пользователя, а не измеренный инвентарь. Ниже разделены факты legacy-реализации, принятые правила rewrite и операционные проверки перед переносом. Все решения D-01…D-16 сохраняются по [реестру решений](06-product-questions.md); выбранное S3-хранилище и основания выбора описаны в [решении о хранилище](08-s3-storage-decision.md). По D-16 весь текущий UI и поведение v27 одобрены 14 ноября 2026 и закреплены в [baseline](prototype/accepted-baseline.json); этот runbook не добавляет экраны или действия к макету. Реальные операции с данными этим редактированием документа не выполняются.

## 1. Факты: текущая SQLite-модель

Источники схемы: [AppDbContext](../../tag-files-service/TagFilesService.Infrastructure/AppDbContext.cs), [актуальный EF snapshot](../../tag-files-service/TagFilesService.Infrastructure/Migrations/AppDbContextModelSnapshot.cs), [начальная миграция](../../tag-files-service/TagFilesService.Infrastructure/Migrations/20250622200914_Initial.cs) и последующие миграции. Это ожидаемая схема после применения всех миграций; реальную версию нужно установить по `__EFMigrationsHistory` на копии БД.

Все прикладные `Id` имеют CLR-тип `uint`, SQLite-тип `INTEGER`, первичный ключ и генерацию значения; начальная миграция задаёт `Sqlite:Autoincrement`. CLR-диапазоны не означают наличие соответствующих `CHECK` в SQLite. `NULL` в таблицах ниже разрешён только там, где это указано. Строковые лимиты реализованы в моделях, но не в SQL-схеме.

### LibraryItems

| Поле | SQLite / NULL | Смысл и источник значения |
| --- | --- | --- |
| `Id` | `INTEGER`, нет | Идентификатор записи библиотеки. |
| `FileName` | `TEXT`, нет | Ключ объекта в `library`, обычно случайное имя; это не исходное имя пользователя. |
| `UploadedOn` | `TEXT`, нет | CLR `DateTime`. Конструктор задаёт `DateTime.UtcNow` при создании записи библиотеки после обработки. Это не время начала загрузки, не EXIF и не S3 LastModified. |
| `FileType` | `TEXT`, нет | Имя enum `FileType`, конвертер EF в строку. |
| `Description` | `TEXT`, да | Описание; модель допускает максимум 150 символов. |
| `CollectionId` | `INTEGER`, да | CLR `uint?`; логическая ссылка на коллекцию. В миграциях нет FK и индекса для этого поля. |
| `VideoDuration` | `INTEGER`, да | CLR `TimeSpan?`, хранится в .NET ticks, 1 tick = 100 ns, 10 000 000 ticks = 1 s. История изменения формата ниже. |
| `ThumbnailStatus` | `TEXT`, нет | Имя enum `ThumbnailStatus`. |
| `IsFavorite` | `INTEGER`, нет | CLR `bool`, приложение использует `false`/`true` (0/1); конструктор задаёт `false`. |
| `LastView` | `TEXT`, да | CLR `DateTime?`; `IncrementViewCount` записывает `DateTime.UtcNow`. |
| `ViewCount` | `INTEGER`, нет | CLR `int`; миграция добавляет с SQL default 0, конструктор задаёт 0. |

[LibraryItem](../../tag-files-service/TagFilesService.Model/LibraryItem.cs) определяет поведение полей. В SQLite нет уникальности `FileName`, ограничения длины описания, проверки положительности счётчика или SQL-ограничений допустимых enum. Времена создаются приложением как UTC, но SQL-столбец `TEXT` сам не подтверждает timezone, точность и формат исторических значений.

### Остальные таблицы

| Таблица | Поля и ограничения |
| --- | --- |
| `Tags` | `Id INTEGER NOT NULL PK`; `Name TEXT NOT NULL`. Модель: 1–50 символов, только Unicode-буквы, цифры и `-`. SQL unique по имени отсутствует. |
| `LibraryItemTag` | `LibraryItemId INTEGER NOT NULL`, `TagsId INTEGER NOT NULL`; составной PK `(LibraryItemId, TagsId)`; FK к `LibraryItems.Id` и `Tags.Id`, оба `ON DELETE CASCADE`; отдельный индекс `TagsId`. |
| `Categories` | `Id INTEGER NOT NULL PK`; `Name TEXT NOT NULL`; `TagQuery TEXT NULL`; `ItemsType TEXT NULL`. Имя 1–200 символов в модели. `ItemsType` — строковое имя `FileType?`. Категория хранит запрос, а не список связей с материалами; `TagQuery` нужно перенести без переписывания смысла. |
| `Collections` | `Id INTEGER NOT NULL PK`; `Name TEXT NOT NULL`. Имя 1–200 символов в модели; unique отсутствует. |
| `ProcessingFiles` | `Id INTEGER NOT NULL PK`; `OriginalFileName TEXT NOT NULL`; `LibraryFileName TEXT NOT NULL`; `FileType INTEGER NOT NULL`; `Status INTEGER NOT NULL`; `CollectionId INTEGER NULL`. Оба enum здесь хранятся числами, конвертеров в строки нет. Нет FK к коллекции или записи библиотеки, времён, checksum, размера, числа попыток, lease, текста ошибки и unique по именам. |

См. [Tag](../../tag-files-service/TagFilesService.Model/Tag.cs), [Category](../../tag-files-service/TagFilesService.Model/Category.cs), [LibraryCollection](../../tag-files-service/TagFilesService.Model/LibraryCollection.cs), [ProcessingFile](../../tag-files-service/TagFilesService.Model/Processing/ProcessingFile.cs). Удаление коллекции удаляет только строку `Collections`, не очищая `CollectionId` у материалов: возможные висячие ссылки требуется выявить, а не молча отбросить ([handler](../../tag-files-service/TagFilesService.Library/Handlers/LibraryCollections/DeleteLibraryCollectionHandler.cs)). Ожидается служебная EF-таблица `__EFMigrationsHistory`; она не заменяет проверку реального `sqlite_schema`.

### Enum: точные значения

| Enum | Значения в порядке CLR / значение INTEGER |
| --- | --- |
| [FileType](../../tag-files-service/TagFilesService.Model/FileType.cs) | `Unknown=0`, `Text=1`, `Image=2`, `Video=3`, `Audio=4` |
| [ThumbnailStatus](../../tag-files-service/TagFilesService.Model/ThumbnailStatus.cs) | `NotGenerated=0`, `Generated=1`, `Failed=2` |

`ThumbnailStatus` в БД библиотеки использует имена, не числа. `FileType` требует двух разных правил импорта: строки из `LibraryItems`/`Categories`, ordinal из `ProcessingFiles`. Сериализация API строками enum не меняет формата SQLite.

### История схемы и опасный участок VideoDuration

| Миграция | Изменение |
| --- | --- |
| `20250622200914_Initial` | Создаёт базовые таблицы; `VideoDuration` — `TEXT`, CLR `TimeSpan?`. |
| `20250716221835_AddCollections` | Добавляет `Collections` и nullable `LibraryItems.CollectionId`, без FK. |
| `20250815135444_AddViewCount` | Добавляет nullable `LastView` и `ViewCount` с default 0. |
| `20250929211941_ChangeVideoDurationType` | Меняет ожидаемый тип `VideoDuration` на nullable `INTEGER`/`long`. |
| `20250929214538_FixVideoDurationDataConversion` | Исполняет SQL-преобразование только строк, для которых `typeof(VideoDuration)='text'`. |
| `20260322165707_AddCollectionIdToProcessingFile` | Добавляет nullable `ProcessingFiles.CollectionId`, без FK. |

[Исправляющий SQL](../../tag-files-service/TagFilesService.Infrastructure/Migrations/20250929214538_FixVideoDurationDataConversion.cs) берёт часы, минуты и секунды из фиксированных позиций `HH:mm:ss`, дробь дополняет/обрезает до семи цифр. Это не универсальный парсер .NET `TimeSpan`: дни (`d.hh:mm:ss`), отрицательные значения, часы шире двух знаков и нестандартные строки нельзя считать безопасно обработанными. Применённая миграция не доказывает корректность длительностей. Обратное преобразование в `Down` этой исправляющей миграции отсутствует.

В import необходимо сохранить исходное значение и SQLite `typeof`, версию схемы и результат преобразования. INTEGER читать как 64-битное целое без промежуточного float; текст разбирать строго, отдельными известными форматами, неизвестное отправлять в отчёт. Не умножать уже существующие ticks повторно и не интерпретировать их как миллисекунды. Для сохранения точности целевой канонический формат можно оставить `duration_ticks INTEGER`; UI получает явно вычисленные секунды. Нулевая длительность не равна неизвестной: текущий обработчик оставляет `TimeSpan.Zero`, если не смог получить `Total` из FFmpeg. Точность самого парсера FFmpeg ограничена миллисекундами ([VideoConversionProgress](../../tag-files-service/TagFilesService.FilesProcessing/VideoConversionProgress.cs)).

## 2. Факты: объекты и обработка медиа

### Бакеты, ключи и метаданные

| Бакет | Ключ | Содержимое и связь |
| --- | --- | --- |
| `temporary` | Исходное имя из `InitiateUploadRequest.FileNames`, без добавленного upload ID | Загруженные браузером байты. Имя может повторяться: это коллизия общего namespace, а не стабильный идентификатор загрузки. |
| `library` | `ProcessingFile.LibraryFileName` → `LibraryItem.FileName` | Случайный GUID без дефисов + расширение в нижнем регистре; для `Video` всегда `.mp4`. `SetFileType` генерирует новое имя ещё раз. |
| `thumbnail` | Основа `LibraryItem.FileName` + `.jpg` | JPEG-обложка, производная от объекта `library`. |

Названия зафиксированы в [Buckets](../../tag-files-service/TagFilesService.Model/Buckets.cs), генерация ключей — в [ProcessingFile](../../tag-files-service/TagFilesService.Model/Processing/ProcessingFile.cs), замена расширения — в [LibraryItem](../../tag-files-service/TagFilesService.Model/LibraryItem.cs). После создания записи на объект `library` пишется S3 object tag `item-id=<LibraryItem.Id>`; это не пользовательские теги библиотеки. Пользовательские теги находятся только в SQLite. Для MP4 явно устанавливается `Content-Type: video/mp4`, для обложки — `image/jpeg`; остальные объекты сервер копирует из `temporary`. Копирование HTTP/S3-метаданных и фактические заголовки нужно инвентаризировать через API, не выводить из расширения.

В `LibraryItems` не сохраняются исходное имя, исходный MIME, исходный размер, checksum, кодеки, размеры изображения, ссылка на upload/job и отдельный признак наличия оригинала. `ProcessingFiles` сохраняет исходное и конечное имя, но не имеет FK к материалу; корреляция возможна по `LibraryFileName`, с проверкой неоднозначностей. API собирает пути `library/<FileName>` и `thumbnail/<stem>.jpg` на лету, причём thumbnail path выдаётся только при статусе `Generated` ([LibraryItemDto](../../tag-files-service/TagFilesService.Library/Contracts/LibraryItemDto.cs)).

### Что происходит после upload

1. [InitiateUploadHandler](../../tag-files-service/TagFilesService.Library/Handlers/InitiateUploadHandler.cs) создаёт `ProcessingFile` в `WaitingForUpload` и выдаёт presigned PUT в `temporary` на десять часов. PUT выполняет браузер напрямую в MinIO.
2. [BucketWatcher](../../tag-files-service/TagFilesService.FilesProcessing/BucketWatcher.cs) слушает события создания объектов, читает только `Records[0]`, берёт `key` и `contentType`, отправляет команду обработки.
3. [FileProcessingHandler](../../tag-files-service/TagFilesService.FilesProcessing/Handlers/FileProcessingHandler.cs) распознаёт MIME-префиксы `image/` и `video/`. Иначе пробует `ffprobe`, который ищет video stream. `Text` и `Audio` существуют в enum, но этот путь их явно не назначает. Находит первую запись `WaitingForUpload` по исходному имени или создаёт новую; сохраняет `Pending`, кладёт объект в память.
4. Один [FilesProcessingService](../../tag-files-service/TagFilesService.FilesProcessing/FilesProcessingService.cs) последовательно читает очередь. Видео всегда прогоняется через `ffmpeg -c:v libx264 -preset veryfast -crf 23 -c:a aac -b:a 128k -f mp4 -movflags +faststart`; preset/CRF читаются из конфигурации. Результат сначала создаётся в локальном `Path.GetTempPath()`, затем загружается в `library`. Для остальных типов выполняется S3 CopyObject без перекодирования.
5. После появления объекта `library` удаляется `temporary/<OriginalFileName>`, затем создаётся `LibraryItem` с `Description=null`, переданным `CollectionId`, текущим временем и остальными начальными значениями; далее записывается object tag `item-id`.
6. Для изображения и видео FFmpeg создаёт JPEG шириной 300 px с сохранением пропорций (`scale=300:-1`); у видео берётся момент на 10% длительности. Ошибка обложки записывает `ThumbnailStatus=Failed`, но обработка материала завершается `Done`.

**Следствие:** архив `library` содержит доступные приложению медиа. Для видео это уже перекодированная версия с потенциальной потерей качества; успешно обработанный исходный видеофайл удалён из `temporary`. Называть все эти файлы «оригиналами» нельзя. Для не-видео текущий путь сохраняет байты загрузки через CopyObject, однако происхождение каждого исторического объекта без проверки не доказано. Rewrite должен перенести имеющиеся медиа без нового перекодирования. Для будущих загрузок принято хранить готовую версию и preview без дополнительного оригинала; автоматическое удаление временного исходника допускается только после проверки сохранённого результата. Это решение не восстанавливает уже удалённые legacy-исходники.

## 3. Факты и выводы: consistency и незавершённая работа

Текущая очередь — [unbounded Channel в памяти](../../tag-files-service/TagFilesService.FilesProcessing/FilesProcessingQueue.cs), а запуск сервиса только читает эту очередь: обхода `ProcessingFiles` для восстановления нет. DB-статусы сохраняются между запусками, запланированное выполнение — нет. Повторное событие, потерянное событие или остановка между шагами могут оставить разные состояния. Это вывод из порядка операций, а не утверждение о наличии конкретной поломки в пользовательских данных.

| Граница сбоя | Возможный результат, который должен обнаружить importer / recovery |
| --- | --- |
| `Pending` сохранён, enqueue не завершён или процесс перезапущен | Работа есть в SQLite, но не исполняется. |
| `library` создан, следующий SQL save/удаление temporary не завершены | Лишний объект или две версии байтов в разных бакетах. |
| `temporary` удалён, `LibraryItem` ещё не сохранён | Конечные байты есть, исходника нет, записи библиотеки может не быть. |
| Строка библиотеки сохранена, S3 tag/status save не завершён | Материал существует, job может быть `Failed`, `item-id` может отсутствовать. |
| Обложка записана, SQL status save не завершён | Обложка есть, API её не показывает. |
| Повторное уведомление после первой обработки | Возможно создание нового job; уникальность по upload ID не обеспечена. |

[DeleteLibraryItemHandler](../../tag-files-service/TagFilesService.Library/Handlers/DeleteLibraryItemHandler.cs) пытается удалить обложку лишь для `Generated`, ловит ошибки удаления S3 и всё равно удаляет строку БД. Поэтому лишние файлы также возможны после удаления. Статус не является доказательством наличия/отсутствия байтов. [GetProcessingFilesHandler](../../tag-files-service/TagFilesService.FilesProcessing/Handlers/GetProcessingFilesHandler.cs) скрывает `Done` и `Failed`, поэтому пустой список в UI не доказывает отсутствие ошибок и остатков.

Целевой протокол rewrite: durable jobs в той же SQLite, уникальный upload ID, явные состояния и retry, ограниченное число параллельных процессов, lease/heartbeat, попытки и причина ошибки. Job после рестарта сверяет существующие S3-объекты и выполняет следующий идемпотентный шаг. SQL-транзакция не охватывает S3: нужны durable incoming, проверка результата PUT/CompleteMultipartUpload полным GET, короткие SQL-транзакции и периодическая сверка ссылок. Атомарную публикацию и fsync объектных файлов выполняет gateway; приложение и migration tool не пишут в его filesystem. Удаление item окончательное, без корзины и периода восстановления; нового UI-входа или подтверждения удаления в одобренном макете нет. Внутреннее состояние удаления/очередь очистки нужно только для завершения удаления после сбоя: оно не даёт Undo и не вводит срок хранения удалённых материалов. В публичной части библиотеки появляются только проверенные готовые объекты. State machine зафиксирована в [архитектуре](03-target-architecture.md) и не реализуется миграционным инструментом.

## 4. Принятые границы целевого хранилища

Подтверждённый сценарий — один пользователь, браузер и Docker Desktop на том же современном Mac. Библиотекой управляет Tag Files; открытие активного хранилища и ручное изменение файлов через Finder не входят в сценарий. Базовый deployment состоит из двух сервисов: Go-приложение с собранной React SPA, SQLite, durable jobs и FFmpeg и **SeaweedFS 4.53 `weed mini`**. Master, volume server, filer/S3 и embedded LevelDB2 работают в одном storage-процессе; PostgreSQL не нужен. Прикладная SQLite и весь persistent state SeaweedFS находятся в разных Docker-managed named volumes на Linux FS; scratch FFmpeg выделен отдельно. Рекомендация Go + React обоснована отдельно в [решении о прикладном стеке](09-application-stack-decision.md); прикладная схема описана в [архитектуре](03-target-architecture.md), выбор S3 — в [решении о хранилище](08-s3-storage-decision.md). Только app публикуется на loopback; внутренний S3 endpoint не имеет host port, browser получает медиа с HTTP Range через same-origin app proxy. Внутренний S3 key не становится пользовательским идентификатором.

Используется один private bucket `tag-files`, без anonymous policy. Логические S3 keys генерируются приложением и не зависят от пользовательских имён, коллекций или тегов:

```text
bucket: tag-files
  primary/<library-id>/<asset-id>/media.ext
  previews/<library-id>/<asset-id>/<profile>/poster.jpg
  incoming/<library-id>/<upload-id>/source
```

Primary и preview публикуются по immutable keys: новые байты или новый профиль получают новый asset ID/key, существующий ключ не перезаписывается другим содержимым. В целевой SQLite `assets` хранят `bucket` и `object_key` с уникальностью пары, размер, SHA-256, Content-Type и provenance; `relative_path` не используется. Все обычные записи, чтения и удаления объектов, включая миграцию, идут через S3 API. Сервис приложения и migration tool не монтируют object root для прямых записей.

Новые загрузки принимают только фото и видео. После обработки остаются готовая основная версия и preview, без дополнительного сохранённого оригинала. Основная версия сохраняет исходное разрешение фото/видео; уменьшение preview не меняет это требование. Вход сохраняется как durable `incoming/.../source`, а подтверждённые части незавершённого multipart upload связаны с durable upload state в SQLite. Даже свежий успешный CompleteMultipartUpload проверяется через HEAD и полный GET/hash incoming **до** постановки processing job в очередь; один SUCCESS-ответ не считается доказательством публикации. FFmpeg использует scratch-копии входа и результата; scratch не заменяет durable incoming. Временный исходник автоматически удаляется через S3 только после успешного canonical PUT/CompleteMultipartUpload с действующим глобальным fsync rule, полного GET с проверкой размера/SHA-256 и требуемого разрешения и commit связанных asset/item/job в SQLite. Ошибка этих шагов оставляет вход для retry. Ошибка preview сохраняется как durable job для восстановления из проверенного primary; доступные готовые preview тоже проверяются перед публикацией. Промежуточные input, output, части MPU и FFmpeg scratch учитываются в резерве диска, хотя дополнительный оригинал не входит в готовую библиотеку.

До любых ingest/migration writes внешний storage preflight через `weed shell` применяет и сохраняет глобальное правило `fs.configure -locationPrefix=/ -fsync=true -apply`, затем после перезапуска проверяет его сохранность и действие на PUT/MPU. Префикс `/` охватывает также служебные multipart paths; более специфичные правила не должны отключать fsync. Параметры `volume.fsyncMinBatchBytes`, `volume.fsyncMinBatchRequests` и `volume.fsyncBatchWait` настраивают batching и сами fsync не включают. Анализ кода 4.53 подтверждает синхронизацию data/index и записи LevelDB2 при этом правиле; реальная crash/power-loss проверка остаётся обязательной. S3 API и app readiness сами не видят фактическую синхронизацию volume и не доказывают её успешным PUT: внешний preflight фиксирует storage configuration, mounts и результаты проверок до открытия writers. [Правило](https://github.com/seaweedfs/seaweedfs/wiki/Path-Specific-Configuration), [data/index sync](https://github.com/seaweedfs/seaweedfs/blob/4.53/weed/storage/volume_write.go#L628), [LevelDB2 sync](https://github.com/seaweedfs/seaweedfs/blob/4.53/weed/filer/leveldb2/leveldb2_store.go#L136).

Storage volume сохраняет **весь `/data`**, включая volumes/chunks и индексы, master state и filer metadata. В официальном Docker image `filer.toml` хранит embedded LevelDB2 в `/data/filerldb2` независимо от `-dir`. Любой override `filer.toml` и его фактические local metadata paths проверяются отдельно: все persistent paths должны быть смонтированы и включены в backup вместе с конфигурацией. Сохранение только chunks или только SQLite приложения не восстанавливает S3 namespace. Xattrs не являются специальным базовым требованием выбранного SeaweedFS-профиля. [Mini и Docker paths](https://github.com/seaweedfs/seaweedfs/blob/4.53/weed/command/mini.go#L391), [Filer Stores](https://github.com/seaweedfs/seaweedfs/wiki/Filer-Stores).

D-15 касается live pending/error очереди новой версии, а не внешнего legacy archive: старые ProcessingFiles и их имена/исходные статусы сохраняются в архиве целиком по прежнему runbook. Готовые legacy items получают upload_id=NULL; им не выдумываются runtime sessions или история Uploads. У новых ready items сохраняется UNIQUE upload_id как origin identity/result lookup без FK на удалённую session.

Ограничение новых загрузок не является фильтром миграции. Переносятся **все** исторические материалы и метаданные, включая `Unknown`, `Text`, `Audio`, если они есть, все теги/связи, коллекции, категории, счётчики, timestamps и историю `ProcessingFiles`. Одна коллекция остаётся аналогом папки для item, множественная классификация выполняется тегами. Запросы категорий переносятся с прежним результатом; дальнейшее переименование тега обновляет зависимые фильтры без изменения их результата.

Сохранить старые числовые ID материалов, тегов, категорий и коллекций, когда нет конфликта: это упрощает проверку и сохранение ссылок. В целевой SQLite это `INTEGER` / Go `int64`, без искусственного сброса последовательности; API ID остаётся в диапазоне безопасного JavaScript integer. Если ID меняются, обязательны полные таблицы соответствия. Целевой `library-id` назначается один раз на библиотеку и сохраняется между повторами инструмента. `asset-id` — непрозрачный UUID; отображение из `(source_snapshot_id, owner_old_item_id, role, bucket, object_key, version_id)` создаётся один раз и сохраняется в журнале отдельного инструмента. Если несколько legacy rows ссылаются на один key, каждому item создаётся собственная проверенная primary-копия без объединения пользовательских записей. Raw-инвентарь source object сохраняется один раз, mapping владения — отдельно. Hash служит проверке целостности; дедупликация разных items при первой миграции не выполняется.

`duration_ticks INTEGER` читается и записывается Go-сервисом как nullable `int64` в единицах 100 ns, без промежуточных float, секунд или `time.Duration`. Миграция сохраняет точное исходное целое, включая значения вне safe integer JavaScript; raw INTEGER в JSON-журнале/manifest передаётся decimal-строкой либо целочисленным токеном с типизированным int64 decoder, без float round-trip. Публичный API по-прежнему возвращает `durationSeconds` для отображения; сортировка и проверка переноса используют точные ticks.

Исходный S3 key хранится как данные и сохраняется точно в manifest; его не подставляют в целевой key или локальный путь. Учитываются `/`, `..`, абсолютные имена, Unicode/case и спецсимволы. Целевые keys строятся из проверенных library/asset/upload ID и заданного layout; обычный path join не является URL encoding. Для локального sandbox и archive инструмент запрещает symlink-выход из root и перезапись БД/конфигурации импортируемыми путями. Произвольные legacy keys не подставляются в целевой layout.

У успешно обработанного legacy-видео primary — имеющийся MP4 с `provenance=legacy_transcoded`. Повторного перекодирования при переносе нет. Найденные исторические исходники и неопознанные объекты тоже сохраняются в отдельном migration archive; правило будущих загрузок не разрешает выбрасывать старые данные. Связь исходника с item должна подтверждаться историей и байтами: совпадения пользовательского имени недостаточно. Это архив отдельного инструмента, а не новый режим originals в основном сервисе.

Обязателен отчёт происхождения и доступности для каждого item:

| Доказательство из источника | Primary provenance | Состояние исходника в отчёте |
| --- | --- | --- |
| Legacy job и объект подтверждают стандартную обработку Video → MP4 | `legacy_transcoded` | `unavailable`: библиотека хранит перекодированную копию, исходник среди сохранённых объектов не найден. |
| Не-видео прошло стандартный CopyObject; checksum перенесённых байтов совпал | `legacy_copied` | `retained_as_primary` для байтов этой загрузки; отдельно указать основание и наличие исходного имени. |
| Нет достаточной истории или запись/тип неоднозначны | `legacy_unknown` | `unknown`: primary сохранён, историческое происхождение не выдумано. |
| Найден отдельный исходник с доказанной связью и проверенными байтами | По реальному происхождению primary | `present_verified`: ссылка на файл отдельного migration archive и checksum. |
| Основное медиа не найдено | Не объявлять primary готовым | `missing_primary`, метаданные сохранены, item отражён в отчёте исключений; до отдельного принятия владельцем исключение блокирует cutover. |

В отчёте хранить old item ID, primary asset ID, bucket/key/version, доказательства, статус доступности и замечания. Отсутствие байтов в source не доказывает их отсутствие во внешних архивах пользователя. По D-12 у готового материала нет пользовательского названия: `LibraryItems.FileName` остаётся источником служебного mapping, а `ProcessingFiles.OriginalFileName` сохраняется в полном внешнем архиве исходных processing rows. Восстанавливать из него новое поле `originalName`/`displayName` или подменять неизвестное имя GUID не требуется. Это не разрешает удалять исторические строки, Description, metadata или доступные байты.

Целевой `media_kind` сохраняет `Unknown`, `Text`, `Image`, `Video`, `Audio`, чтобы не изменить старые search/категории. Для legacy `Text`/`Audio` достаточно безопасного скачивания attachment; расширенный viewer/player миграцией не обещается. Значение за пределами enum сохраняется как raw и требует разбора, без молчаливого удаления или замены на `Unknown`.

## 5. Отдельный инструмент: воспроизводимая offline migration

Миграция — **отдельный одноразовый скрипт или standalone tool**, который читает старую систему и строит новую библиотеку. Его исходники, зависимости, image и инструкция отделены от основного сервиса. Export/import/migration не входят в код, HTTP API, UI или CLI приложения; основной service image не получает migration subcommands. Основной сервис умеет читать уже подготовленную целевую схему, но не запускает legacy importer при старте.

Внешний инструмент может остаться на C# для точного чтения legacy `TimeSpan`/EF-схемы либо использовать Python с точным разбором ticks и типов SQLite. Это не добавляет .NET или Python в runtime Go-приложения. Целевой DDL и версия схемы инструмента согласованы с теми же versioned SQL migrations, которые Go-сервис встраивает и применяет через Goose; совпадение схемы проверяется на fixture до переноса. История EF относится к source, Goose — к целевой прикладной схеме. [Embedded SQL migrations Goose](https://github.com/pressly/goose#embedded-sql-migrations).

Пользователь разрешил offline-перенос с полной отдельной новой копией, примерно ещё 100 GB плюс резерв; старые данные сохраняются для rollback. Ни online migration, ни сокращённое окно, ни перенос без дополнительной копии не являются нерешёнными продуктовыми вопросами. Ниже runbook будущего инструмента: скрипты сейчас не реализованы и не запускались. Полный dry run, затем финальный проход выполняются одной проверенной версией инструмента. Перекодирование, исправление неоднозначных метаданных и удаление orphan-объектов не смешиваются с переносом.

### 5.1. Инвентаризация и пробный запуск

На согласованной копии SQLite получить `sqlite_schema`, `PRAGMA user_version`, `PRAGMA journal_mode`, `__EFMigrationsHistory`, `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, счётчики строк и максимум ID. Снять raw-значения/`typeof` длительностей и времён, неизвестные enum, отрицательные счётчики, дубли имён и файлов, висячие `CollectionId`, осиротевшие связи тегов. Не запускать старый web service на оригинале для диагностики: его [Program.cs](../../tag-files-service/TagFilesService.WebHost/Program.cs) автоматически вызывает `Database.Migrate()` при старте.

Примеры read-only запросов на копии:

```sql
SELECT MigrationId, ProductVersion FROM __EFMigrationsHistory ORDER BY MigrationId;
SELECT typeof(VideoDuration), COUNT(*) FROM LibraryItems GROUP BY typeof(VideoDuration);
SELECT Id, VideoDuration, typeof(VideoDuration), UploadedOn, LastView FROM LibraryItems;
SELECT FileName, COUNT(*) FROM LibraryItems GROUP BY FileName HAVING COUNT(*) > 1;
SELECT i.Id, i.CollectionId FROM LibraryItems AS i
LEFT JOIN Collections AS c ON c.Id = i.CollectionId
WHERE i.CollectionId IS NOT NULL AND c.Id IS NULL;
SELECT Status, COUNT(*) FROM ProcessingFiles GROUP BY Status;
```

Через S3 API собрать инвентарь всех трёх бакетов: точный key/version, размер, LastModified, ETag, Content-Type, пользовательские metadata и object tags. Установить versioning/lifecycle/encryption, наличие multipart uploads и объектов без строк в БД. ETag — метаданные источника, не универсальная SHA-256. Внутренние файлы `minio_data` не являются контрактом обычных медиа.

Сопоставить библиотеку с `library` строго по `FileName`; проверить обложки независимо от статуса; сопоставить все processing rows по сохранённым именам с проверкой неоднозначностей. Отчёт выделяет полные записи, недостающие медиа, недостающие обложки, лишние объекты, незавершённые jobs и неоднозначности. Все неопознанные объекты и их метаданные сохраняются в quarantine/migration archive без автоматического добавления в библиотеку. История `ProcessingFiles`, включая `Done` и `Failed`, сохраняется в архиве целиком; она не превращается автоматически в runnable jobs. Ничего не удалять при аудите.

Dry run включает всю схему, связи и реальные форматы значений. Медиа-fixtures охватывают маленькие/большие файлы, Unicode, все пять legacy media kinds, отсутствующую обложку и остатки processing; при отсутствии реальных `Text`/`Audio` нужны синтетические примеры. Проверить restart инструмента между S3 PUT/CompleteMultipartUpload, полным проверочным GET и SQL commit: повтор использует прежний mapping и не теряет/не дублирует данные. Отдельный storage preflight подтверждает сохранённое global fsync rule, все persistent paths, HEAD/Range и MPU SeaweedFS 4.53 на штатном named Linux volume; даже свежий Complete SUCCESS проверяется HEAD и полным GET/hash до SQL commit. Полный пробный перенос даёт фактические время, место и список исключений.

### 5.2. Зафиксировать source и остановить writers

1. Сохранить версии/дигесты старых images, compose, конфигурацию, mount paths и точку возврата. Не менять исходную схему для удобства инструмента.
2. Закрыть upload и изменения метаданных, избранного, view-count и удаления. Учесть браузеры с уже выданными десятичасовыми PUT URL.
3. Дать начатым работам завершиться до срока из runbook, например 30 минут. `Failed` не считается успешным drain. По истечении срока остановить обработчик и сохранить все processing rows/temporary-объекты как незавершённые. Не ждать бесконечно из-за `WaitingForUpload`.
4. Остановить старый backend/worker и проверить отсутствие FFmpeg writers. Закрыть S3 PUT/DELETE для всех клиентов, включая старые presigned URL и anonymous policy; оставить только локальный read-only доступ инструменту. Остановка backend сама по себе не блокирует прямую запись в MinIO.
5. Создать и проверить согласованный SQLite snapshot через SQLite Backup API / `.backup`. Копирование одного открытого `.db` недостаточно при WAL: WAL является частью persistent state. [SQLite Backup API](https://www.sqlite.org/backup.html), [WAL](https://www.sqlite.org/wal.html).
6. Зафиксировать полный MinIO-инвентарь и сохранить старое хранилище для rollback без изменения объектов. При cold-copy всего native volume остановить и MinIO; копировать весь volume, а не выборочные внутренние файлы. Зафиксировать snapshot ID, время freeze, хеш SQLite snapshot и manifest. Независимая дополнительная копия source, если она предусмотрена пользовательской политикой backup, учитывается отдельно от обязательной новой библиотеки.

После freeze инструмент читает только SQLite snapshot (`mode=ro`; `immutable=1` лишь для действительно неизменяемой автономной копии) и логически неизменяемый S3 source с read-only credentials. Для экспорта native MinIO snapshot использовать отдельный изолированный MinIO той же версии на рабочей копии: сервер может изменять служебные данные, поэтому сохранённый rollback snapshot нельзя назначать его рабочим volume. Не запускать старое и новое приложения как writers на общих файлах.

Целевая библиотека создаётся в **новых пустых named volumes** metadata SQLite и S3 storage при остановленном новом приложении. Во время миграции работает только целевой SeaweedFS 4.53 `weed mini`; внешний storage preflight сохраняет и проверяет глобальное `fs.configure -locationPrefix=/ -fsync=true -apply` до ingest. Инструмент получает S3 endpoint/credentials и создаёт private bucket `tag-files` через API. Временный tools container получает metadata volume для целевой SQLite, read-only snapshot/источник и отдельные mounts для журнала/архива и ограниченного sandbox. Весь `/data` SeaweedFS доступен на запись только storage-процессу и не монтируется в migration container. Источник читается через MinIO GET, назначение записывается через S3 PUT/MPU и проверяется S3 HEAD/полным GET/hash. Source и destination задаются раздельно и проверяются до записи. Приложение не монтирует legacy source и не выполняет инструменты. После проверки временный контейнер удаляется, оба целевых volumes сохраняются.

### 5.3. Идемпотентный перенос и checkpoints

Инструмент создаёт `run-id`, связывает его с неизменяемым `source_snapshot_id` и сохраняет durable mapping в отдельной SQLite журнала. Минимальная запись на объект: source bucket/key/version/size/ETag/metadata/tags, SHA-256, целевые asset ID, bucket/object_key, ожидаемые размер/хеш, состояние (`planned`, `copying`, `verified`, `imported`, `quarantined`, `error`), timestamps, попытки и причина; для MPU — upload ID и подтверждённые parts. Для строк БД сохранить старые/новые ID, raw-поля и преобразования. Канонический manifest с собственным хешем — переносимый отчёт отдельного инструмента, не продуктовый export API. Журнал/архив не хранятся только в одноразовом контейнере.

Порядок для одного объекта:

1. Найти или создать стабильное mapping, проверить неизменность source snapshot и инвентаря.
2. Прочитать frozen source через MinIO GET, посчитать полный SHA-256 и размер и записать байты через destination S3 PUT либо MPU в `tag-files` по заранее назначенному immutable key. Допустим поток или ограниченный sandbox инструмента; прямые filesystem writes в storage root запрещены. Для MPU дождаться успешного CompleteMultipartUpload и в следующем шаге проверить публикацию даже при свежем SUCCESS. Сохранённое глобальное fsync rule обязательно до начала записи.
3. Выполнить destination HEAD и **полный destination GET**, заново вычислить SHA-256/размер и сравнить с source. HEAD, ETag и сохранённое поле checksum не заменяют чтение байтов; нужные Content-Type и metadata проверяются отдельно. При ошибке зафиксировать её, не объявлять объект готовым и не удалять source.
4. Зафиксировать `verified` в журнале. После сбоя проверить назначенный key полным GET: совпадающий объект использовать повторно, отсутствующий загрузить; mismatch не перезаписывать и не скрывать новым mapping. Незавершённый MPU возобновляется только после проверки source version и parts либо явно abort/retry по тому же mapping. Лишний объект после сбоя до SQL commit обнаруживается сверкой.
5. Короткой SQL-транзакцией добавить item/asset/связи с `bucket`/`object_key` или отметить существующий стабильный mapping. Зафиксировать checkpoint. Restart сверяет S3 и БД, затем продолжает с первого незавершённого шага. Источник сохраняется для rollback независимо от checkpoints.

Категории, raw `TagQuery` и `ItemsType` сохраняются без изменения смысла. Перевод запросов на стабильные tag ID подтверждается сравнением **наборов item ID** для каждой категории до/после. Неоднозначные одинаковые имена и неразбираемые выражения попадают в отчёт; автоматическая подмена по похожему имени запрещена. Rename в новом сервисе обязан сохранять проверенный результат. Значения длительностей переносятся по правилам раздела 1, с raw value и `typeof` в журнале.

Незавершённые legacy jobs не запускать вслепую. Сначала сверить library object, item row, temporary object, object tag и thumbnail. При проверенном конечном медиа перенести его без повторной конвертации; недостающая обложка может восстанавливаться из сохранённого primary. Если остался только исходник, сохранить его в архиве с legacy job и явным результатом recovery; это не новый upload и не повод потерять `Unknown`/`Text`/`Audio`. При отсутствии всех медиа сохраняются метаданные и исключение для разбора владельцем. Исторические статусы сами по себе не разрешают удаление байтов. Каждое принятое исключение имеет ID, причину и решение владельца; уже принятое исключение не блокирует переход, но остаётся в отчёте и не превращается в заявление о восстановленных байтах.

### 5.4. Свободное место и время

Перед запуском измерить байты каждого source бакета/версий, число объектов, БД/WAL, самый большой файл и MPU, свободные байты/inode metadata volume, object root, migration sandbox/archive и scratch. На Mac отдельно проверить предел/свободное место Linux virtual disk Docker Desktop и свободное место macOS, где лежит disk image. Свободные 200 GB в Finder не гарантируют 200 GB внутри Linux volume; увеличение logical disk limit не создаёт свободное место host. [Настройки диска Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/). Старый MinIO и новый S3 одновременно занимают место; `temporary`, архив и неизвестные объекты входят в расчёт, даже если не видны в UI. GB ниже десятичные; preflight считает байты.

`T` — все переносимые байты, включая quarantine, обложки, версии и отдельные primary copies при общих legacy keys; `W` — provider-independent пик незавершённых PUT/MPU, временного состояния хранилища, входа и sandbox, измеренный в pilot; `D` — целевая БД, filer/master metadata, индексы и журналы; `R=max(10 GB, 10% размера целевых данных)` — рекомендуемый эксплуатационный резерв. Суммарное дополнительное свободное место перед стартом: **`T + W + D + R`**, с раздельным расчётом для source MinIO, destination S3, metadata и sandbox на каждом фактическом диске. Уже занятый source не освобождается и не считается доступным резервом. При исходных 100 GB на том же диске дополнительно нужны примерно ещё 100 GB плюс рассчитанный пик и накладные расходы. Пользователь разрешил такую полную копию; точный расчёт является preflight-проверкой, а не новым запросом продуктового решения. Дополнительный backup, промежуточный archive или native snapshot без COW требуют места сверх новой библиотеки. Полномасштабная изолированная rehearsal/restore-drill копия для app/browser/recovery также учитывается отдельно: ещё одна полная пара metadata/storage volumes плюс её временный пик и scratch; fixture-drill не доказывает sizing полной библиотеки.

Миграция не перекодирует видео. Временный дисковый пик PUT/MPU, completion, отложенной очистки и повторов зависит от реализации выбранного storage; его измеряют на SeaweedFS 4.53 в pilot с репрезентативными большими файлами и заданной параллельностью. К нему отдельно добавляются полный source в sandbox, если он используется, и для новых загрузок durable incoming, canonical candidates, preview и FFmpeg input/output scratch. Не переносить модель сборки частей другого provider на SeaweedFS и не назначать без замеров коэффициент «два размера объекта» либо иной максимум. Лимит параллельности выводится из измеренного бюджета с резервом. COW/reflink может экономить начальное место, но не заменяет независимый backup.

**Hardlink между MinIO internals и целевыми медиа запрещён.** Не создавать hardlink исходной SQLite и не считать hardlink резервной копией. Базовый перенос строит отдельную полную копию обычных проверенных байтов, без hardlink и без зависимости от сохранности старых inode.

Нижняя оценка stream-copy — `T / фактическая end-to-end скорость`; независимое контрольное чтение добавляет время. Для 100 GB при 50 MB/s это около 33 минут на перенос и ещё 33 минуты на перечитывание; при 20 MB/s — около 83 минут на каждый проход. Это арифметические примеры: общий диск, hashing, S3 overhead, мелкие файлы, archive и приёмка увеличивают длительность. Offline-окно рассчитывается по полному dry run с запасом, например ×1,5; короткий простой не обещается.

| Stop gate | Действие |
| --- | --- |
| До старта не хватает рассчитанного места/inode или нет проверенной точки возврата | Не запускать финальный перенос. |
| Свободное место ниже `R` либо не покрывает оставшиеся байты + `W+D+R` | Приостановить инструмент на безопасном checkpoint; не освобождать место удалением source. |
| Checksum mismatch, изменение frozen source или ошибка чтения обязательного медиа | Остановить cutover, сохранить журнал, повторить перенос/разбор. |
| Missing media, потеря строк/связей или неоднозначное преобразование без принятого решения | Не объявлять миграцию полной; сохранить всё доступное и перечень исключений для разбора владельцем. Принятые исключения с ID/причиной/решением не блокируют cutover и остаются в отчёте. |
| Истекло окно из runbook | Сохранить checkpoint и вернуть старый deployment, пока новые writers ещё не открыты. |

### 5.5. Проверка, cutover и rollback

До переключения получить машинно читаемый отчёт:

- `integrity_check = ok`, `foreign_key_check` без нарушений целевой модели; counts и mapping **всех** старых ID согласованы, включая legacy kinds и архив истории.
- Значения после зафиксированных преобразований совпадают: описание, тип, длительность, favourite, timestamps, счётчики, collection, теги. Сравниваются наборы связей; `NULL` не превращается в пустую строку или 0. Служебные имена и processing rows сохранены во внешнем mapping/archive; пользовательские названия медиа не создаются.
- Результат каждой категории совпадает по item ID; rename используемого тега сохраняет результат.
- У каждого обязательного объекта проверены полный размер и SHA-256 через destination GET; assets содержат правильные bucket/object_key. Количество и сумма байтов source согласованы с imported + archive/quarantine + зарегистрированными отсутствиями; молчаливые пропуски и потеря типов недопустимы. Отдельный реестр перечисляет принятые исключения с ID/причиной/решением и оставшиеся нерешённые ошибки.
- Статусы обложек согласованы с файлами. Производную обложку можно восстановить; thumbnail не заменяет отсутствующее основное медиа.
- Автоматический probe проверяет открываемость фото/видео без перекодирования. Ручная выборка охватывает большие/старые файлы, Unicode, все legacy kinds, поиск, категории, коллекции, избранное, сортировки, HTTP Range и перемотку. Probe не заменяет checksum.

Закрыть инструмент и его SQLite-соединения. При остановленном app проверить целевую пару внешними read-only tools: SQLite `mode=ro`, S3 GET/HEAD/Range и полный GET/hash через SeaweedFS той же закреплённой версии; внешний storage preflight подтверждает сохранённое global fsync rule и mounts. Исходную проверенную пару не запускать с app ради приёмки: startup recovery, workers и view-count являются writers. Browser/recovery/FFmpeg-проверки обычного app выполняются на отдельной изолированной расходуемой копии либо fixture; полномасштабная rehearsal-копия требует дополнительного места по разделу 5.4. После acceptance остановить storage оригинальной проверенной пары, переключить основной порт/конфигурацию на неё и запустить SeaweedFS и обычное приложение со всеми штатными writes. Не менять mounts работающего процесса. Старые backend/worker остаются выключенными, source, архив и журнал сохраняются; frozen rollback baseline не использовался при browser/recovery-тестах. До первой новой записи rollback состоит в остановке обоих новых сервисов и запуске старого deployment на сохранённой согласованной точке.

Открытие записи — отдельная точка runbook. После неё старый snapshot не содержит новых upload, правок, view-count и удалений. Возврат без их переноса теряет данные и не называется безопасным rollback. При проблеме остановить оба новых сервиса и сохранить согласованную пару metadata/storage volumes с конфигурацией и секретами; предпочтителен repair/restore новой библиотеки. Если нужен возврат в старый формат, post-cutover delta и обратный перенос выполняет отдельно проверенный standalone tool, а не CLI приложения. Наличие такого инструмента не предполагается автоматически и не блокирует подготовку прямой миграции. Не удалять сохранённый source до успешной приёмки; дальнейший срок хранения владелец выбирает в своей политике резервирования.

## 6. Docker и повседневная эксплуатация

Текущий [compose.yml](../../compose.yml) размещает SQLite в `./data/tag-files.db`, весь MinIO volume в `./data/minio_data`, публикует S3 API `5010`, MinIO console `5011`, backend `5001`, frontend `4200`. Backend получает весь `./data:/app/data`; FFmpeg output создаётся в container `/tmp`, отдельный persistent scratch mount не задан. [Dockerfile](../../tag-files-service/Dockerfile) устанавливает FFmpeg через apt при сборке; версии пакетов и базовые images не закреплены digest. [compose-dev.yml](../../compose-dev.yml) использует образы `latest`. Готового backup/restore runbook в этих deploy-файлах нет.

Для rewrite нужен минимальный compose из **двух сервисов** с закреплёнными версиями/дигестами: app с SPA/API, SQLite, durable jobs и FFmpeg и storage `chrislusf/seaweedfs:4.53` с `weed mini` и сохранённым глобальным fsync rule. Отдельный metadata named volume содержит прикладную SQLite и её persistent state, storage named Linux volume — весь `/data` SeaweedFS, включая master/filer/volume state; FFmpeg получает явный scratch с ограничением места и уборкой. Прикладной сервис не монтирует storage volume. Заданы UID/GID и права, health/readiness, graceful shutdown для jobs и порядок запуска storage → app. Liveness storage проверяет живость процесса; S3 HEAD/GET и app readiness проверяют доступность нужного bucket, а не физическую flush durability. Отдельный внешний storage preflight проверяет конфигурацию `fs.configure -locationPrefix=/ -fsync=true -apply`, сохранность правила после restart и фактические persistent paths/mounts; app не выводит эти свойства из S3-ответа и не получает Docker socket. Startup не создаёт anonymous policy. По умолчанию публикуется только `127.0.0.1:4200:8080`, SPA/API/media работают с одним origin, S3 endpoint `http://storage:8333` доступен app и временным tools containers по внутренней Docker-сети. Основной сервис не получает backup destination, scheduler или доступ к legacy source; нужные mounts создаются лишь у отдельных tools containers на время операции. Удалённая установка, LAN и несколько пользователей в подтверждённый сценарий не входят.

Основная платформа — Apple Silicon `linux/arm64`, существующая `linux/amd64` — вторичная. FFmpeg работает внутри Linux VM: наличие VideoToolbox на macOS не означает доступность в контейнере. Базовый путь — программная обработка с concurrency 1; замеры на Mac ещё не проводились. Приёмка измеряет этот путь, сохранение исходного разрешения и временный диск на реальных фото/видео. Ускорение/concurrency требуют отдельной проверки. Mac sleep, restart Docker Desktop и принудительная остановка входят в recovery-проверки.

SQLite живёт на Linux FS metadata named volume; WAL, `synchronous=FULL`, `foreign_keys=ON`, busy timeout и короткие транзакции задаются приложением. Commit item/asset/job должен быть durable до удаления incoming. Master/filer/volume state SeaweedFS живёт на отдельном named Linux volume; bind mount macOS для активных SQLite/storage и сетевой volume не являются базовой конфигурацией. Библиотека не требует Finder-доступа. Второй app-процесс-владелец той же библиотеки получает отказ. Migration tool пишет целевую SQLite только при остановленном app, а S3-объекты — через работающий SeaweedFS; backup/restore tools получают native volumes только после остановки обоих сервисов. Приложение никогда не применяет DDL к legacy source. Данные не модифицируются в обход S3 API в обычной работе: chunk layout и embedded metadata являются внутренним форматом SeaweedFS.

Логический размер библиотеки, свободное место доступных приложению metadata/scratch volumes, oldest queued job, retries/failed jobs и найденные missing/orphan objects относятся к операционным логам и внешним проверкам. Одобренный UI содержит пользовательскую pending/error очередь Uploads, без отдельного Settings/diagnostics screen и технической панели в медиатеке. **S3 API не сообщает физическое свободное место storage volume и фактическую fsync durability**: байты/inode и storage configuration проверяет отдельный внешний read-only operational preflight контейнера. App не монтирует `/data` SeaweedFS и не получает Docker socket ради этой метрики; недоступное значение в операционном отчёте помечается как неизвестное, а не как «места достаточно». Capacity/preflight учитывает внешний замер, storage reserve и scratch раздельно. Журналы резервирования, последнее успешное копирование и restore drill относятся к отдельному скрипту и инструкции владельца; встроенной backup-страницы нет. Для одного пользователя достаточно прикладных статусов и логов, распределённая очередь/кластер наблюдаемости не нужны.

Существующая [инициализация бакетов](../../tag-files-service/TagFilesService.Infrastructure/BucketInitializer.cs) задаёт новым бакетам anonymous `GetObject`, `PutObject`, `DeleteObject`; старые policy не проверяет. Поэтому при миграции нельзя считать старый S3 read-only лишь после остановки backend. В новом локальном deployment private bucket `tag-files` доступен по credentials, а browser получает медиа через app на loopback; S3 endpoint находится только во внутренней Docker-сети. SeaweedFS запускается с явно настроенными credentials: режим Allow All без credentials недопустим. Отдельный IAM и versioning в базовую схему не входят. Это требование к freeze и целевому deployment, а не утверждение о доступности текущего экземпляра из интернета.

## 7. Отдельные backup/restore script и инструкция

Резервные копии — ответственность пользователя. В основном сервисе нет export/import/backup API, UI, scheduler или CLI. Нужны отдельные backup/restore scripts с runbook: они управляют Docker с хоста и запускают временный tools container с нужными mounts. Скрипты версионируются отдельно от прикладного кода; app image не используется как maintenance CLI. Расписание, носители, retention и RPO выбирает и обеспечивает владелец, автоматическое расписание приложения не создаётся.

Базовый протокол полностью offline: сначала остановить **app целиком** с upload, workers и cleanup, дождаться завершения процесса, затем остановить **SeaweedFS mini** и проверить отсутствие всех writers. Копирование native volumes выполняется только при остановленных **обоих** сервисах. Это исключает view-count, S3 PUT/DELETE, уборку MPU и изменение filer/master/volume state; режим «UI открыт только для чтения» сам по себе недостаточен. Online snapshot/pinning в этот scope не входят. Для 100 GB простой включает время полного копирования и проверки, его измеряет runbook.

Backup сохраняет согласованные **прикладную SQLite + весь SeaweedFS `/data` + конфигурацию**, включая незавершённую работу. Полноценный backup не сводится к `s3 sync` или `fs.meta.save`: нужны chunks/volumes с индексами, master state и embedded filer LevelDB2, скрытые служебные файлы и deployment. Один metadata snapshot не содержит байтов объектов, а одни chunks не восстанавливают namespace и MPU state. Все дополнительные persistent paths из overrides `filer.toml`/storage configuration также включаются в manifest и backup. Простой внешний формат для отдельного скрипта, без универсального прикладного export/import контракта:

```text
backup-<generation>/
  backup.json                   # generation, UTC, schema/app/gateway/tool versions, image digests
  metadata-volume.tar           # SQLite, WAL при наличии и остальной persistent state app
  storage-volume.tar            # весь /data SeaweedFS: master, filerldb2, volumes/indexes, hidden/MPU state
  deployment/                   # compose/config и защищённые secrets для восстановления
  manifest.jsonl                # safe path, role, byte length, SHA-256, filesystem metadata
  complete                      # записывается последним после полной проверки
```

Формат привязан к поддерживаемой версии целевого хранилища и описан в инструкции standalone script. Volume archives создаются и распаковываются **внутри Linux**, с сохранением структуры, прав, владельцев и необходимых файловых атрибутов. Архивируется весь `/data` SeaweedFS, включая фактические master metadata paths, `/data/filerldb2`, data/index files и скрытое служебное состояние; фильтр «только видимые медиа» запрещён. Если `filer.toml` переносит metadata за пределы `/data`, внешние persistent paths и сам override сохраняются вместе с этим поколением. Xattrs не являются специальным базовым требованием SeaweedFS: обязательны полнота native state и доказанное восстановление выбранным archive/tool. Архив можно хранить как обычный файл на внешнем macOS-носителе. Копирование отдельных внутренних файлов через Finder не является проверенным native backup. [SeaweedFS backup](https://github.com/seaweedfs/seaweedfs/wiki/Data-Backup), [роль filer metadata](https://github.com/seaweedfs/seaweedfs/wiki/Filer-Stores).

JSONL metadata export, универсальный importer и встроенная переносимость между произвольными схемами не требуются. Для legacy migration отдельный архив дополнительно сохраняет raw-строки SQLite, `ProcessingFiles`, точные S3 key/version/metadata/tags и mapping. Compose/config, версии образов, сохранённое глобальное fsync rule и необходимые credentials сохраняются в защищённой части backup; секреты/токены не публикуются в manifest или логах. В выбранной схеме filer LevelDB2 embedded, внешняя metadata DB не добавляется. FFmpeg scratch можно пересоздать; durable incoming и upload/job state — нельзя.

Порядок backup:

1. Проверить свободное место destination, остановить app, затем SeaweedFS; зафиксировать версии, digests, сохранённое global fsync rule, фактический `filer.toml`, все persistent paths и mounts. Отдельный Linux tools container получает **оба named volumes read-only**, дополнительные persistent mounts при наличии overrides, внешний destination с правом записи и никаких credentials к работающему приложению.
2. Сохранить весь metadata volume, включая возможный WAL после аварийной остановки; не копировать только `.db`, игнорируя WAL. На отдельной временной копии создать согласованный SQLite snapshot и проверить `integrity_check`/связи. Если требуется recovery с записью, выполнять его на этой копии, сохраняя source volume read-only.
3. Архивировать весь storage volume `/data` в `.part` нового поколения вместе с master state, filer LevelDB2, volumes/chunks, индексами и скрытым служебным/MPU state; считать хеши и вести checkpoints. Сохранить размеры, права, владельцев и состав файлов, а также все внешние metadata paths при overrides. Для partial upload сохраняются SQLite session/MPU ID, параметры частей, известный контентный fingerprint и ordered part manifest для `completing` с partNumber/ETag; storage archive сохраняет filer metadata и chunks частей, сверяемые после запуска через ListParts. Для queued job нужен durable incoming. FS restore является отдельной offline операцией над целым согласованным native state, а не способом загрузки объектов в работающий S3.
4. Перечитать archive/destination и проверить размер/SHA-256 всех файлов, полный состав native state и согласованность manifest с БД. Сохранить app config/secrets и storage configuration. Не очищать старое поколение до проверки нового. Завершить generation атомарным rename и marker `complete`; неполный архив, отсутствие filer/master state или chunks не считается backup. Обязательный restore drill ниже подтверждает пригодность формата и инструмента.
5. Сохранить отчёт о времени, байтах, полноте native metadata/data, результате проверки и checkpoint. Удалить tools container и запустить SeaweedFS, затем app с прежней парой volumes; внешний storage preflight подтверждает сохранённое global fsync rule до открытия writers. При ошибке сохраняется предыдущий проверенный backup, исходная библиотека не изменяется скриптом.

Restore выполняется при остановленных **app и SeaweedFS** в **два новых пустых named Linux volumes**, без перезаписи существующих; дополнительные persistent paths из сохранённой конфигурации восстанавливаются согласованно. Tools container получает backup read-only и новые metadata/storage volumes как destination. Сначала проверяются version/completeness, safe paths и отсутствие symlink-выходов, затем archives распаковываются внутри Linux с восстановлением структуры, прав и владельцев; сверяются полный состав master/filer/volume state, размеры/хеши и SQLite integrity/relations. Используются checkpoints; неполная или смешанная пара volumes не переключается в deployment. Scratch создаётся заново. Это восстановление native backup целиком, а не прямые объектные записи в работающий S3 server.

На восстановленной паре при остановленном app запускается изолированный SeaweedFS mini **той же закреплённой версии** с восстановленной конфигурацией; внешний preflight проверяет сохранённое global fsync rule, фактические metadata paths и их persistence. Внешние read-only tools проверяют SQLite `mode=ro`, S3 GET/HEAD/Range, полные hashes, Content-Type, пользовательскую metadata и private bucket. ListParts проверяет текущий состав подтверждённых частей по session/MPU ID: partNumber, ETag, размер и доступные checksum; для `completing` сверяется ordered part manifest и incoming через HEAD/полный GET/hash. Приложение на этой проверенной паре пока не запускается: специального runtime read-only/maintenance режима не требуется. Полноценный app с recovery запускается только на отдельной изолированной расходуемой копии или fixture. Там проверяются reset старых leases, ListParts/retry, свежий Complete SUCCESS → HEAD/полный GET/hash до queue, queued либо сохраняемая pending/error для незавершённых jobs, отсутствие истории ready/cancel и идемпотентный lookup готового item по upload_id после удаления session. Receiving без восстановимого MPU/input после restore остаётся видимой ошибкой: пользователь повторно выбирает файл для проверяемого resume/явной новой передачи либо вручную отменяет прежнюю задачу; автоматических expired/cancelled по возрасту нет. Byte-offset локального файла не является контрактом resume.

D-15 restore drill отдельно содержит failed input, старую idle/receiving session, ready item с уже удалённой session и незавершённый cleanup receipt после ready/cancel. Возраст snapshot не удаляет очередь или inputs. Проверяются повтор Complete/GET по items.upload_id, отсутствие FK на удалённую session, восстановление cleanup из самостоятельных owned keys/MPU/in-flight intents без строки Uploads и сохранение видимой ошибки при потерянном MPU. Timeouts/leases восстанавливают исполнение, но не очищают ошибку без действия пользователя. Внешний срок хранения backup/migration archive не меняется.

**Restore drill обязателен** для выбранного archive/tool и при изменении его версии или формата; полнота и согласованность master/filer/volume state проверяются, а не предполагаются по расширению архива. Drill включает ready items, legacy kinds, bucket/object metadata, durable incoming, partial MPU upload и queued job; app/browser/recovery-сценарии выполняются на расходуемой копии/fixture, исходная проверенная восстановленная пара остаётся baseline. Браузерный File handle не восстанавливается. При повторном выборе файла resume с существующими parts разрешён только после совпадения его **контентного fingerprint** с зафиксированным для исходного входа: имя, размер и clientFileId сами по себе идентичность не доказывают. После проверки клиент передаёт недостающие части по сверке ListParts/part manifest. Если исходный fingerprint недоступен или не совпал, старые parts не переиспользуются; после явной повторной отправки пользователем создаётся новая session. После acceptance host orchestration останавливает storage проверенной пары, подключает именно эту оригинальную пару volumes и запускает SeaweedFS и обычный app со всеми writes после внешнего storage preflight. Предыдущая пара volumes и backup сохраняются для возврата; frozen rollback baseline не используется как рабочая копия при тестах. Restore drill измеряет RTO; наличие архива или успешный `s3 sync` не подтверждают возможность восстановления. После новых записей действует то же ограничение rollback, что в разделе 5.5.

Backup destination находится **за пределами обоих named volumes** и disk image Docker Desktop, например на выбранном пользователем внешнем носителе. Reset/удаление volume/disk image и uninstall могут уничтожить активную библиотеку. Docker описывает [резервирование volume отдельно от image](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/) и [удаление локальных volumes при uninstall](https://docs.docker.com/desktop/uninstall/). Не читать/копировать активные named volumes через внутренности Docker disk image; использовать документированные mounts временного Linux-контейнера. Перед reset/uninstall владелец проверяет внешний backup и restore полного native state в чистую пару volumes.

Частота резервирования определяет RPO, фактический restore — RTO. Скрипт и инструкция объясняют эти последствия и место под полное поколение обоих volumes, archive sandbox и восстановленную пару; они не назначают владельцу график или дополнительные поколения. Cleanup активной библиотеки не должен затрагивать внешние backup. Отдельные исторические migration archive и исходный deployment также сохраняются по выбранной владельцем политике, а не удаляются автоматически приложением.

## 8. Операционные preflight-проверки

Продуктовые решения по originals, offline-простою, полной новой копии, управлению библиотекой и ответственности за backup приняты. Перед фактическим запуском остаются проверки экземпляра, а не новые блокеры продуктового проектирования:

- Установить реальную версию схемы, raw-типы длительностей/timestamps, integrity, дубли, dangling references и все media kinds. Для неоднозначных значений сохранить исходное представление и отчёт.
- Измерить байты/версии объектов, самый большой файл, multipart/encryption и остатки temporary. Проверить доказательства original provenance и сохранность исходного mapping/processing archive, не создавая пользовательское название для item.
- Проверить фактическую ёмкость host и Docker disk image, inode, source MinIO, destination S3, metadata, migration sandbox/archive и FFmpeg scratch; учесть измеренный provider-independent временный пик PUT/MPU, input/scratch, отдельную целевую копию, резерв и любое дополнительное поколение backup/restore, выбранное владельцем.
- Проверить закреплённый SeaweedFS 4.53 `weed mini` на `linux/arm64` и `linux/amd64`, embedded LevelDB2 и persistence всего `/data`/overrides, сохранённое global fsync rule до ingest, private bucket `tag-files`, immutable keys, полный GET/hash, HEAD/Range и MPU. Свежий Complete SUCCESS тоже проверяется HEAD/полным GET/hash до queue/commit. S3 API/readiness не заменяют внешний storage preflight; прямых filesystem writes миграцией и app нет.
- Замерить полный dry run и контрольное чтение; записать длительность offline-окна, checkpoints, stop gates и командный порядок возврата в standalone runbook.
- Сверить сохранность всей истории `ProcessingFiles` и неопознанных объектов в архиве, результаты всех категорий и проверенный source для rollback.
- Для backup script проверить остановку обоих сервисов, внешний destination, полноту SQLite и всего SeaweedFS master/filer/volume state со скрытыми файлами и metadata paths из overrides, защищённые config/secrets и изолированный restore внутри Linux с проверкой S3-доступа и hashes; носитель, частоту и retention ведёт владелец вне основного сервиса.

Подготовка standalone tools и synthetic fixtures не требует повторного обсуждения уже принятых продуктовых решений. Неустранённый checksum mismatch, неразобранная потеря данных или отсутствие проверенной точки возврата останавливают фактический cutover, а не разрешают молчаливое исключение старых записей.
