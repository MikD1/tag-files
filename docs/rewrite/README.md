# Подготовка Tag Files к production переписыванию

Исследование фиксирует реализованные возможности прототипа и архитектуру новой реализации с переносом существующей библиотеки. Рекомендуемый стек после дополнительного сравнения: **Go + React SPA**, SQLite с долговечной очередью и локальный S3 **SeaweedFS 4.53 `weed mini` с embedded LevelDB2 и global fsync**. App и storage запускаются двумя контейнерами в одном Compose deployment. Новую версию разрабатывают AI-агенты; контракты, SQL и проверки заранее закрепляются. Ответы владельца продукта внесены в [реестр решений](06-product-questions.md); остальные продуктовые детали сохраняют текущее поведение.

Дата исходного исследования: 10 ноября 2026 года; выбор S3 и стека приложения обновлён 11 ноября, единый viewer по D-14 согласован 12 ноября. **14 ноября текущий UX-макет и реализованное пользовательское поведение утверждены как целевые по D-16**; документы приведены к этому baseline. Исследованный commit: `3d16460b60ab97992f9a7c8817e50a458afe7deb`. Исходники приложения не изменены. Рабочие БД, бакеты и 100 GB медиа не открывались; реализация и UX оценены по исходникам и существующим тестам. Технологии изучены по первичным источникам; для S3 прочитаны также код и registry manifests. Приложения-кандидаты, production-сборки и сравнительные замеры не запускались. Отдельно подготовлен [автономный UX-макет](prototype/README.md) на синтетических данных; результаты Chromium связаны с конкретным SHA-256 сборки, Mac/runtime проверки самого приложения остаются в приёмке.

## Подтверждённые требования

- Один пользователь, selfhosted Docker; браузер на том же современном Mac с Docker Desktop.
- Сохранить все реализованные функции, включая доступные только через API.
- После переписывания добавлять новые функции; заранее не превращать продукт в SaaS или многопользовательский сервис.
- Разработку новой версии выполняют AI-агенты; знакомство человеческой команды с исходным стеком не определяет выбор.
- Сохранить данные нескольких тысяч элементов и около 100 GB медиа; новый формат допустим при безопасной миграции.
- Отдельно оценить концептуальные проблемы и UX/UI; составить вопросы для уточнения продукта.
- Новые загрузки — только фото и видео. Хранится одна рабочая версия после автоматической обработки и preview, без дополнительного архива оригиналов; исходное разрешение сохраняется.
- Коллекция — аналог папки с единственным членством, множественная классификация — теги. Rename тега обновляет фильтры категорий без изменения результатов.
- Удаление окончательное, без корзины. Библиотекой полностью управляет Tag Files.
- Галерея и просмотр минималистичны: медиа и теги в центре внимания, без названий материалов, технических сведений и постоянных подсказок. Имена иконок доступны через tooltip и assistive technology; ошибки показываются по ситуации. Отдельной кнопки справки поиска нет. Служебные metadata и legacy-данные при этом сохраняются.
- Интерфейс и демонстрационный контент английские. Типы переключаются двумя независимыми иконками, сортировка открывает меню семи пунктов с иконками, добавление — icon-only; accessible names и keyboard/focus сохраняются. Русская документация и поддержка Unicode в пользовательских данных остаются.
- По решению от 12 ноября используется один viewer из grid/list/related. Медиа сверху, теги/коллекция и уместный контекст ниже, без правой панели. Два legacy режима объединяются с сохранением действий и правила учёта через 3 секунды; производные preview/poster assets остаются.
- D-15 от 14 ноября: Uploads — только незавершённые и ошибочные задачи, без истории и TTL. Ready/cancel убираются сразу; ошибки и inputs остаются до успешного retry/ручной отмены. Отдельный durable cleanup не удерживает строку, повтор готового upload разрешается через items.upload_id. Общая HTTP-идемпотентность и внешняя backup retention сохраняются.
- Согласованный UI baseline `tag-files-ui-v1` (v27) охватывает все пять разделов, единый viewer и редактор: grid без selection, list с выбором и массовой заменой, скрываемый sidebar с icon rail, keyboard search тегов/одной коллекции и стабильный диалог. Точная сборка и исходники закреплены в [паспорте baseline](prototype/accepted-baseline.json); этот интерфейс не требуется проектировать заново.
- Legacy migration — отдельный одноразовый скрипт. Допустимы остановка старой версии и полная отдельная копия. Backup/restore обеспечивает пользователь внешними средствами; скрипты и инструкция отделены от основного сервиса.

## Основные выводы

Категория в прототипе — сохранённый поиск, коллекция — ручная группа с единственным членством, «похожие» — точное совпадение непустого набора тегов. Избранное хранится как флаг; отдельная рабочая страница отсутствует. Массовое назначение тегов/коллекции, удаление item и создание тега реализованы в API и легко теряются при восстановлении продукта только по UI.

Самые существенные архитектурные риски: очередь в памяти и зависимость от событий S3; отсутствие общего протокола согласованности метаданных и объектов; строковые категории, связанные с именами тегов; преждевременное удаление input до надёжной фиксации результата. Отказ от дополнительных оригиналов — подтверждённая политика. Для Mac выбран SeaweedFS mini в named volume и один browser origin. Хранилище отвечает за физическое размещение объектов и multipart, согласованность S3/SQLite остаётся обязанностью приложения. Формат библиотеки документируется для отдельных offline migration/backup/restore scripts; основной сервис ими не управляет. Backup сохраняет весь Seaweed state: metadata, chunks и configuration. Перед production нужны SDK, durability и restore проверки.

Go + React рекомендуется для нового кода с явным SQL и генерируемыми API-контрактами. .NET 10 + React остаётся сильной альтернативой с более длинной поддержкой серверной ветки. Переход на Go не обещает ускорения FFmpeg или исчезновения протоколов надёжности. React SPA использует один согласованный набор router/cache/UI/forms; обязательные старые viewer-функции проверяются до закрепления нового пакета. Выбор стека не добавляет возможностей продукту автоматически.

Миграция переносит существующие байты, а не обещает восстановить удалённые video originals. Старую библиотеку нужно заморозить, инвентаризировать, скопировать в отдельную цель, сверить все hashes/relations/сценарии и сохранить до принятого перехода. Детали неизвестного состояния настоящих данных выясняются scan на копии; они не подменяются предположением, что DB statuses верны.
