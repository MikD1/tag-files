# Этапы реализации и приёмка production версии

План описывает порядок реализации и проверки нового приложения, а не предписывает немедленно переписывать текущий код. По [D-16](06-product-questions.md) владелец 14 ноября 2026 одобрил [макет v27](prototype/README.md) как целевой UI/поведение; [паспорт baseline](prototype/accepted-baseline.json) фиксирует неизменный artifact. Приёмка включает F-01…F-38, D-01…D-16, весь согласованный UI и production-надежность. Неизвестные параметры реального Mac/библиотеки проверяются operational preflight. Повторный опрос не требуется; отдельный backlog относится только к возможностям вне принятого baseline.

Подтверждённая граница приёмки: новые загрузки принимают только фото и видео, готовая версия сохраняет исходное разрешение, в постоянной библиотеке остаются готовая версия и preview без дополнительной копии original. Обработка, проверенное сохранение результата и последующее удаление входа выполняются автоматически как одна пользовательская операция загрузки, без дополнительного подтверждения. Это правило относится к upload; подтверждение ручного UI-удаления отдельно не обсуждалось и остаётся UX-предложением. Удаление окончательное, без корзины. У элемента не больше одной коллекции, как папки, и несколько тегов; rename тега сохраняет результат категорий и обновляет их актуальный queryText и отображаемые фильтры. Активным хранилищем управляет только Tag Files на том же Mac в Docker Desktop; Finder-доступ к его внутренностям не является пользовательским сценарием.

Legacy-перенос и export/backup/restore выполняют отдельные скрипты по инструкции. Они не входят в код, API или CLI основного сервиса; в приложении нет backup scheduler, кнопок резервирования или статуса последнего backup. Пользователь отвечает за запуск и хранение резервных копий. Миграции собственной versioned schema при обновлении приложения остаются частью основного сервиса и отличаются от одноразового legacy-переноса. Приведённые ниже способы crash recovery, idempotency и проверки целостности — рекомендации реализации подтверждённых требований к сохранности.

D-12 задаёт обязательный визуальный контракт: галерея и просмотр сосредоточены на медиа и тегах. В нормальном состоянии нет filename/title, технической таблицы, описания и постоянных подсказок; справка открывается по запросу, сообщения возникают при ошибке или активной операции. Навигация, favorite, коллекция, редактирование и controls видео достижимы компактно. Это проверяется отдельно от сохранности backend metadata: Description, timestamps, счётчики, MIME и размеры остаются в данных/операциях, а готовый item не получает поля пользовательского названия.

Для media-cards и related thumbnails принят hover/focus popup всех тегов простым неинтерактивным текстом через `·`: без постоянного ряда, chips, ссылок и `+N`. Проверяются keyboard focus/Escape без переноса focus, hover-переход через зазор, расположение под миниатюрой с переносом выше у нижней границы окна, отсутствие обрезания краями/контейнером и grid reflow. Viewer/list теги и Same tags остаются кликабельными; изменение миниатюр не меняет поиск, коллекции или учёт просмотров.

D-13 требует английский UI и демо-контент: проверяются обычные экраны, ошибки, empty/loading states, диалоги, tooltips и accessible names. Пользовательские Unicode-данные и миграция не переводятся. Проверка icon-controls отдельно проходит четыре состояния Image/Video (`00/11` → all, `10` → Image, `01` → Video) с сохранением обоих toggle, Clear и восстановлением context. Sort открывает доступное с клавиатуры icon-menu всех семи English-пунктов, отмечает текущий выбор и возвращает focus. Add/Choose files находятся только в Uploads с доступным English-именем; sidebar Uploads сохраняется. Галерея не содержит Add/upload shortcut, search-help `?` или постоянных type/sort selects.

Grid проверяется без checkbox/selection/bulk UI и без slider. Два controls размера миниатюр `+`/`−` появляются только в grid: увеличение/уменьшение, семь устойчивых уровней, disabled на границах и сохранение после reload; в list они скрыты. Согласованные selection и bulk-команды обязательно проверяются только из list: видимые строки текущей страницы, Selected: N/clear, пустой начальный bulk draft и явное предупреждение полной замены tags/collection. Одна команда заменяет оба поля у всех выбранных items атомарно; add/remove и выбор всех страниц не входят в baseline. Смена page/filter/view и успешный Save очищают selection. Hover/focus текст тегов миниатюр, API и данные от этого не меняются.

В list проверяются четыре колонки Media/Tags/Collection/Actions, правая группа Edit media → checkbox и зарезервированное место без сдвига строки. Hover/focus-within раскрывают оба controls; checked checkbox остаётся видимым после ухода указателя. Opacity-hidden controls доступны Tab и видимы при focus. Edit media открывает прежний single-item editor без viewer/route change, Cancel возвращает focus к исходному Edit и не меняет metadata; сохранение использует прежнюю атомарную команду. Grid по-прежнему без selection.

Photos/Videos/Sort/Clear filters проверяются внутри одной рамки search form, в едином icon-style с кнопками 32 px; Clear filters виден и при пустом фильтре; reset снимает query/type, collection scope и временное подмножество, возвращая page 1 без изменения sort/view. `+`/`−` и Grid/List находятся снаружи справа на той же строке desktop; на узкой ширине группы могут переноситься без overflow. В footer grid/list рядом с пагинацией показан totalItems активной выдачи; header не дублирует его, размер текущей страницы не подменяет общий total. Проверка Clear сохраняет прежний sort, четыре состояния типов и семь сортировок не меняются.

Sidebar проверяется раскрытым по умолчанию, с ручным Expand/Collapse и сохранением preference после reload; CSS не сворачивает его автоматически по ширине. Collapse оставляет rail `72px` со ссылками-иконками Library/Collections/Tags/Categories сверху и Uploads внизу viewport; подписи/бренд скрыты, English title/aria-label, active route и компактный обновляющийся Uploads badge остаются. Все ссылки работают с клавиатуры и указателя без предварительного Expand. Toggle вне aside доступен в обоих состояниях с aria-expanded/controls; ширина workspace меняется без новой header-строки и пересоздания содержимого. Draft/input, viewer/navigation/playback и list selection не сбрасываются. Categories и совместимый alias `#/saved-searches` сохраняют прежнюю модель/API. Debug-кнопка сброса демо не занимает место над Uploads.

D-14 от 12 ноября 2026 объединяет два legacy UI-пути просмотра в один viewer: canonical URL одинаков из grid/list/related, медиа сверху, теги/группа коллекции ниже, правой панели нет; origin хранится в URL/Back без постоянного дополнительного label. Category остаётся сохранённым запросом. Приёмка подтверждает все прежние действия в этом общем пути, Back с query/type/sort/page/scroll, соседей контекста и единый view event через 3 секунды; thumbnails и списки не считают просмотр. Группа коллекции идёт перед Same tags, heading — только кликабельное имя без дублирования у тегов/All, виден даже без siblings при назначенной коллекции. Related Same tags проверяется как exact-set без текущего item; клик heading — обычный AND по всем именам, UploadedDesc/page 1 без прежних filters, с текущим item и дополнительными тегами. Это согласованное изменение UI, а не требование воспроизвести два старых режима. Thumbnail/poster/preview assets и их pipeline сохраняются.

Разделы Tags/Categories проверяются как компактные таблицы Tag/Usage count и Name/Query/Items type; клики имён tag/category/collection создают новую галерею UploadedDesc/page 1 с текущим grid/list: точный tag query без прежних фильтров, category query + type либо collectionId. Back viewer сохраняет origin sort/page; это явное изменение legacy-переходов с сохранением sort. Collections проверяется как auto-fill grid с квадратной обложкой, min 160 px, gap 12 px и именем 14 px под ней, без описаний/отдельного Open media. Total под каждым разделом считает сущности, а не материалы. Проверки выполняются с раскрытым sidebar и rail 72 px без сброса viewer/state. Отсутствие CRUD в исследовательском макете не отменяет production-функции из F-реестра и не разрешает показывать мёртвые кнопки.

Дополнительный synthetic-набор для редактора — 30 тегов и 350 коллекций, приёмочный пример без ограничения максимума; стандартные fixture 8/3 не меняются. Проверяются selected tag chips, исключение выбранных ID, case-insensitive substring обоих полей, навигация ArrowUp/Down без назначения до Enter/click, tag Enter/запятая только для существующего совпавшего имени, Escape/Tab, отсутствие implicit Save и autocreate и назначения только от ввода. Коллекция — одно поле selected name + chevron + inline clear/`No collection`, без chip/второго input: подтверждённый выбор заменяет nullable ID, Escape/Tab/blur возвращают label выбранного draft ID вместо неподтверждённого query. Сравнивается bounding box диалога до/после focus, typing, clear и pick при 0/350 результатах: размеры/позиция не меняются в пределах того же viewport. Floating popup вне layout flow имеет max-height 220px, viewport clamp/flip, не обрезается dialog overflow; в невысоком viewport footer доступен, прокрутка результатов затрагивает только popup; при переполнении chips/полей прокручивается тело формы, header/footer остаются на месте. Cancel не меняет metadata; failed Save сохраняет draft и ввод тегов без фиксации query коллекции, pending Save блокирует поля, повтор и закрытие формы до исхода; Cancel/Close/backdrop/Escape до Save не меняют metadata и возвращают focus. GET collections возвращает весь справочник; Search collections локально ищет буквальную подстроку, clear/no-match и footer shown/total корректны, компактная сетка не меняется, URL-фильтр восстанавливается при Back/reload. Server binary names/ID и D-15 Uploads остаются прежними; API search/pagination справочников в эту итерацию не добавляются.

Технический baseline: modular monolith с SQLite и jobs как источником истины, два контейнера — приложение и **SeaweedFS 4.53 `weed mini` с embedded LevelDB2**, без PostgreSQL. До любых загрузок применяется и сохраняется глобальное правило `fs.configure -locationPrefix=/ -fsync=true -apply`; приёмка подтверждает durability metadata/chunks и сохранность правила после restart. Storage volume содержит весь `/data`, включая `master`, `filerldb2` и `volumes`. S3 endpoint остаётся во внутренней Docker-сети; browser обращается только к same-origin приложению, которое streaming proxy обслуживает upload и media. Выбор и его ограничения закреплены в [решении по S3](08-s3-storage-decision.md). Ниже перечислены обязательные будущие проверки; эта документация не означает, что conformance, benchmark или crash/drill уже запускались.

Рекомендуемый прикладной стек для реализации AI-агентами: Go 1.27.4, стандартный `net/http`, `database/sql` с CGO `mattn/go-sqlite3`, `sqlc` и `goose`, AWS SDK for Go V2; React 19.3.1, Vite 8.3, TypeScript strict, React Router Data mode, TanStack Query, Mantine `core`/`hooks`/`form` и CSS modules. Node 26 используется только при сборке SPA. OpenAPI 3.0.3 служит источником генерации `oapi-codegen` для JSON-контрактов Go и `openapi-typescript`/`openapi-fetch` для TypeScript; binary upload/media обслуживаются отдельными потоковыми handlers. Подробности, альтернативы и ограничения — в [решении по прикладному стеку](09-application-stack-decision.md). Новый стек не ослабляет functional parity, S3 conformance, migration и crash/restore gates.

D-15 от 14 ноября: Uploads содержит только pending/error, без истории и возрастного TTL. Ready после verified primary + SQLite commit и ручной cancel сразу удаляют видимую строку; failed/idle/receiving и необходимый input сохраняются до успешного retry либо cancel. Ready-транзакция публикует item с nullable UNIQUE upload_id (legacy NULL, не FK на session), убирает session/parts/завершённый ingestion job и сохраняет независимый cleanup. GET/Complete после удаления session находят success/itemId по upload_id; отсутствие session и item не создаёт новый импорт. Cancel receipt живёт до остановки readers/writers и окончательного Abort/Delete/reconcile; ready item отменой не удаляется. Общий 7-дневный operation_results, navigation TTL и внешняя backup retention не являются TTL очереди и остаются.

Операционная подготовка | Реестр решений, выбранный S3 baseline и его conformance gate, проверяемая media matrix, целевой Mac profile, инвентаризация места | Defaults применены; реальные форматы, разрешения, disk budget и допустимые исключения зафиксированы; ARM64, persisted global fsync rule и durability metadata/chunks проверены на фактическом Docker volume |
| 1. Production-приложение и контракт внешних инструментов | Два закреплённых container images, app data/scratch и отдельный полный `/data` SeaweedFS, versioned SQLite schema, lock одного владельца; формат библиотеки и контракты внешних скриптов | Чистый install, schema update и restart сохраняют данные; browser видит только app origin, S3 не опубликован на host; исходная библиотека не подключается writable; скрипты отделены от сервиса |

Формат библиотеки и внешний перенос проектируют с первого этапа, а не добавляют после завершения UI. Это не требует legacy importer внутри production-приложения. В каждом этапе полезен законченный вертикальный сценарий; crash/restore проверки распределяют по этапам. Сроки без сведений о команде и media matrix не оцениваются.

## Правила реализации и проверки для AI-агентов

Контекст разработки AI-агентами подтвержден пользователем. Качество обеспечивают контракт и проверяемые границы модулей; не предполагается, что агент лучше пишет React или Go. До распределения задач фиксируются JSON/streaming boundaries, схема и SQL, состояния jobs/uploads и владение client state. Агент получает ограниченную область файлов и соответствующие F/D-контракты; generated files не редактируются вручную, исторические предложения вне D-16 не включаются из-за приоритета в аудите; согласованный v27 не помечается optional.

| Область | Обязательная будущая проверка |
| --- | --- |
| Контракты и генерация | OpenAPI 3.0.3, SQL-запросы и versioned migrations проверяются до зависимого кода. Повтор `oapi-codegen`, `openapi-typescript` и `sqlc` не оставляет необъяснимого diff; CI проверяет воспроизводимость генерации. DTO и обработка ошибок совпадают по Go/TypeScript, safe integer IDs и `durationSeconds` не получают альтернативных полей из внутренних моделей |
| Go и SQLite | `gofmt`, `go vet ./...`, `go test ./...` и `go test -race ./...`; integration с настоящим `mattn/go-sqlite3`, FK/WAL и миграциями `goose`. SQL/lease/transaction tests проверяют независимые ожидаемые результаты. CGO toolchain и production builds подтверждаются для linux/arm64 и linux/amd64, а не предполагаются по успешной host-сборке |
| HTTP и потоки | JSON endpoints используют сгенерированный контракт; upload/GET/HEAD/Range обходят JSON body binding, `ReadAll` и целиковую сериализацию. Проверяются known Content-Length, cancellation, bounded buffers, disconnect и отсутствие скрытого повторного чтения исчерпанного body. S3 signing и body checksum проходят отдельный gate ниже |
| React и client state | `tsc --noEmit`, lint с React Hooks rules и ограничениями импортов features, unit tests для URL codec, state transitions, draft и ошибок. TanStack Query — единственный cache server state; loaders используют тот же cache. URL владеет query/sort/page/seed, форма — draft, localStorage — versioned preferences. SSR/Node runtime, Redux/Zustand, RHF/Zod и дополнительные UI kits не вводятся без конкретной необходимости |
| Просмотры и повторы | React StrictMode, обычный lifecycle и HTTP retry дают одно событие открытия единого viewer после трех секунд с одним event ID; уход раньше отменяет таймер. GET/refetch не меняет views. Save/favorite сохраняют последовательность активного Random context и не создают дубликат команды |
| Browser upload | Worker считает part SHA-256 и полный fingerprint ограниченными порциями; тест исключает полный `file.arrayBuffer()`/`SubtleCrypto.digest` для большого файла. XHR с `Blob`-частями дает progress в Safari; память ограничена выбранным partSize и concurrency. Закрытие диалога не теряет server results; повторный выбор и fingerprint gate обязательны для resume после reload |
| Browser и viewer | Playwright Chromium/WebKit покрывает основные пути и негативные состояния; macOS Safari/Chrome проверяют реальные codecs, keyboard/focus и VoiceOver. Кандидат YARL проходит Zoom/Rotate/Video/Inline gate для одного viewer из всех точек входа; установка пакета или скриншот не являются доказательством parity |

UI использует один Mantine theme и компоненты выбранного семейства. Custom wrappers содержат предметные правила, а не второй универсальный UI framework. Hooks, polling, retry и invalidation имеют явного владельца. Code review сверяет изменение с F-реестром и crash-инвариантами; число сгенерированных строк и заявления агента о завершении не заменяют результатов проверок. Эти команды и browser suites здесь перечислены как будущие gates, а не уже выполнены при подготовке документации.

Каждый ID отмечается конкретным automated test либо ручным шагом с результатом, fixture и версией образа. «Экраны похожи» и число реализованных endpoints не являются проверкой parity. Если новый протокол заменяет legacy endpoint, в матрице указывается его функциональный эквивалент. Намеренное ограничение новых загрузок до фото/видео не разрешает потерять legacy Text/Audio/Unknown, их метаданные, безопасное скачивание и прежние результаты фильтров.

Исторические F-факты не переписываются из-за нового дизайна. F-13…F-15 трассируются в единый viewer: отказ от отдельного quick-preview одобрен D-14 при сохранении всех media/actions и контекста. Например, прежняя колонка даты или счётчик в detail могут быть скрыты по D-12, но их данные, сортировки и операции продолжают проверяться. Отдельный UI-check подтверждает отсутствие вымышленных заголовков и служебных полей в галерее, list и едином viewer; у иконок при этом сохраняются accessible names и keyboard/focus-доступ.

## Набор контрольных данных

Небольшой синтетический набор должен включать фото/видео для новых загрузок и все пять legacy kinds: Image/Video/Unknown/Text/Audio; 0/1/несколько тегов; одинаковые и различающиеся tag sets; case-sensitive/Unicode/дефисные и legacy duplicate tag names; категории с AND/OR/NOT и unresolved terms; пустую и непустую коллекцию; item без коллекции; Description NULL и непустое значение; favorite; нулевые и ненулевые views/lastView; duration NULL/0/дробь/больше суток; одинаковые upload timestamps; missing/failed poster. Добавить одинаковые client filename у разных uploads и повтор одного содержимого. Новые Text/Audio/Unknown и non-media файл с поддельным MIME фото/видео должны проверять отказ в приёме, а не создание ready item неизвестного типа.

Для медиаполитики нужны фото и видео с разными исходными разрешениями, portrait/landscape, orientation/rotation metadata и необходимой конвертацией. Проверять размеры готового primary с учётом orientation, отсутствие скрытого уменьшения разрешения, воспроизведение и preview. После успешной автоматической очистки остаются готовая версия и preview, дополнительный original не хранится. Совпадение исходных байтов после конвертации не требуется: сохранение разрешения не означает lossless codec. В legacy-наборе доступная перекодированная копия остаётся primary; удалённый старым приложением original не выдумывается.

Golden queries берутся из [текущего контракта](01-current-behavior.md) и [новой спецификации](02-product-specification.md). Сравниваются множества ID для фильтров и последовательности для сортировок. NULL следует текущему ASC-first/DESC-last; новый поиск/refresh меняет Random порядок, а обход одной выдачи сохраняет его; tie-breaker уточняет прежнее неоговорённое равенство. Для duplicate names отдельно сравнивается global statistics, которая исторически группируется по имени.

## Надёжность и сохранность

Обязательные проверки с инъекцией остановки приложения и gateway в разных точках:

1. До/после CreateMultipartUpload и записи его ID в SQLite, до/после durable part binding и forwarding body, после подтверждённого или неподтверждённого UploadPart; при timeout ListParts/CompleteMultipartUpload и между Complete 200, incoming HEAD и полным GET/hash; до claim и после claim job.
2. Во время FFmpeg с входом в incoming S3 и локальным scratch; после conversion, до/после сохранения candidate expected SHA-256/size, во время canonical PUT, после потери PUT-ответа, до/после полного GET/hash и SQLite `ready` commit, до/во время удаления incoming.
3. Во время preview PUT/проверки и фиксации derivative job; при рестарте scratch может исчезнуть, но durable incoming либо проверенный primary остаётся доступен для продолжения.
4. При повторных UploadPart того же номера с теми же и другими байтами, concurrent complete/cancel и CAS receiving→completing; во время drain известных writers, AbortMultipartUpload, delete cleanup, истечения lease, restart и позднего запроса/ответа старой generation. Отдельно задержать уже принятые storage UploadPart/Complete до cancel и возобновить после первой успешной очистки.
5. В отдельном legacy-скрипте во время copy/metadata commit; во внешнем cold backup при остановленных app и gateway до complete marker.

Отдельные контрактные проверки: create collection/saved search → commit → потеря HTTP-ответа → повтор с тем же Idempotency-Key даёт тот же ID; GET operations показывает результат. Saved search → tag rename → apply/reload/name-only PATCH сохраняют множество ID через savedSearchId, актуальный queryText и UI содержат новое имя. Saved search `cat` → create duplicate `cat` → assign новому item → apply включает этот item; create разрешает соответствующий неизвестный term, а rename не перепривязывает чужой unresolved term. Нельзя перенести отсутствие дополнительного подтверждения в upload pipeline на ручное удаление item: проверяются два разных сценария.

Для durable upload проверяется порядок: SQLite binding `(session, partNumber, expectedSize, SHA256)` **до forwarding body** → S3 UploadPart с реально проверяемой checksum → CAS receiving→completing и drain известных writers → durable ordered part manifest → CompleteMultipartUpload в `incoming/<library-id>/<upload-id>/source` → **после каждого успеха HEAD + полный GET/hash incoming** → queued commit → canonical PUT в `tag-files` → полный GET/hash → fenced SQLite `ready` commit → cleanup incoming. Complete 200 с отсутствующим, неполным или неверным incoming не создаёт queued/job/ready и даёт наблюдаемую ошибку/reconcile. Digest заголовка браузера не считается проверенным до body validation storage; ETag остаётся непрозрачным, checksum части/composite не заменяет полный SHA-256 файла.

Проверки part binding включают сохранение до первого S3 вызова, потерю HTTP-ответа, повтор тех же size/digest/bytes и 409 без forwarding для другого digest или размера того же номера. Неверный body при прежнем digest обязан отвергаться именно S3 checksum validation. Lease/generation не считается отменой запроса, уже принятого storage: остановка app между передачей части и ответом, запуск новой generation и поздний UploadPart должны сохранить те же байты; другой body не может пройти checksum gate. Complete закрывает новых writers и дожидается известных активных отправок. При `InvalidPart` manifest не заменяется слепо: reconcile принимает новый ETag только при доказанном совпадении part binding/размера/SHA256, неизвестная или чужая часть оставляет явную ошибку.

Для каждого publication attempt/lease generation до PUT сохраняются durable candidate ID/key **и expected SHA-256/size**. Primary использует `primary/<library-id>/<asset-id>/media.ext`, preview — `previews/<library-id>/<asset-id>/<profile>/poster.jpg`. Проверяются crash после записи intent до PUT, потеря ответа и исчезновение scratch: тот же candidate переиспользуется только для тех же проверенных байтов; другой результат conversion или новая lease получает новый key. Задержанный PUT старой попытки не меняет текущий canonical, не проходит fenced commit и не перезаписывает mismatch. Известный candidate без reference допускает cleanup. После `ready` session/parts/завершённый ingestion job отсутствуют, item с upload_id сохранён; ошибка удаления incoming оставляет только независимый cleanup receipt/job в диагностике, без строки Uploads; до `ready` ошибка не объявляется успешной публикацией. Poster failure отдельно сохраняет ready primary.

Reconcile обязан различать незавершённый MPU, уже completed incoming и queued processing, используя SQLite intents/bindings, authoritative ListParts и проверяемый объект, а не S3 notification. Потерянный Create/Complete-ответ, повтор part number и concurrent complete/cancel должны завершаться одним устойчивым исходом. Cancel/delete tombstones и durable receipts сохраняются после первого успешного Abort: cleanup повторяет **Abort + HEAD/Delete incoming**, в том числе после late Complete. Задержанное завершение не воскрешает queued job или удалённый item; receipt удаляется только после завершения reconciliation; календарного TTL session нет. Сиротские MPU abort выполняется только при доказанном владении session; неизвестные object keys/MPU попадают в отчёт и не удаляются GC автоматически.

D-15 suite переводит clock далеко за прежние 7 дней: receiving/idle, failed input, queued/running/retry и parts не исчезают по возрасту и не получают auto-expired/cancelled. Проверяются явный retry прежней ошибки, ручной cancel с немедленным удалением строки, fence и late Complete, независимый cleanup после ready/cancel и отсутствие upload_history. После ready проверяется атомарность item.upload_id UNIQUE + удаления session/parts/ingestion job, потерянный HTTP-ответ → повтор Complete/GET возвращает тот же item без session и после истечения общего operation key. Если item затем явно удалён, старый Complete не воскрешает его. Cancel-vs-ready race не удаляет победивший ready item. Общая идемпотентность HTTP с 7-дневным operation_results проверяется отдельно и не служит retention Uploads.

Внешний backup/restore-скрипт запускается только при остановленных app и storage, включая upload writers, worker и cleanup; наличие активного владельца блокирует инструмент. Cold backup сохраняет согласованные SQLite/app data, **весь `/data` SeaweedFS: master state, filerldb2 и volumes с data/index/chunks**, multipart state, persisted global fsync rule и необходимые configuration/secrets. Drill включает ready items, partial MPU с bindings, completed incoming до conversion, готовый candidate с expected SHA-256/size до commit/удаления входа и queued processing. После restore в чистые volumes проверяются конфигурация и global rule до загрузок, metadata/chunks, ListParts и полные hashes; recovery продолжает работу без потери подтверждённых parts, необходимых входов или повторного item. Один metadata snapshot или `s3 sync` не считается таким backup. Scratch не считается единственным источником восстановления. Незавершённый backup без complete marker отвергается внешним restore-инструментом. Результаты инструмента и инструкция отделены от интерфейса и API приложения.

После refresh/restore browser File handle не восстанавливается автоматически. Для повторно выбранного файла tested resume возможен только при совпадении исходного **контентного fingerprint**, затем недостающие parts определяются через ListParts/bindings. Fixture с одинаковыми filename/size/clientFileId и другими байтами не переиспользует parts. Отсутствующий исходный fingerprint тоже запрещает такой resume: новая session создаётся после явной повторной отправки пользователя.

Browser memory suite отдельно измеряет hash worker и upload при максимальном файле и двух одновременных передачах. Серверный `partSize` должен соответствовать и S3 limits, и согласованному browser memory budget; разрешенные S3 5 GiB не становятся разумным client buffer по умолчанию. Полный fingerprint проверяется инкрементальным hasher, часть — тем же согласованным SHA-256 протоколом; перенос хеширования в worker не делает чтение целого файла ограниченным по памяти. Проверяются отзывчивость controls, XHR byte progress в Safari и восстановление pending/error через polling после закрытия диалога/reload и lookup готового item по upload_id без session/history.

Ожидается один логический item на session, повторяемые операции и понятный terminal failure при невосстановимом входе. Принятые входные байты остаются в S3 до проверенной долговечной записи готового primary и SQLite commit; после автоматической очистки сохранность обеспечивает готовая версия, а исходные байты уже не обещаются. Crash после conversion и до удаления incoming должен оставить пригодный вход или проверенный ready asset, после restart завершить cleanup и не создавать дубликат. Отдельно проверяются Mac sleep, Docker Desktop restart, SIGKILL обоих контейнеров и заполнение storage/scratch. Сбой питания/VM проверяется на штатном Docker volume с persisted global fsync rule, включая согласованность metadata/data-index/chunks и доступность подтверждённых parts/objects после запуска; mock exception и успешный process restart не заменяют power-loss проверку.

SQLite integration использует реальный `database/sql` driver `mattn/go-sqlite3`, WAL/FK, сгенерированные `sqlc` запросы и миграции `goose`, не замену SQLite in-memory mock. Media tests используют известные небольшие файлы и реальный FFmpeg; e2e UI использует изолированную временную библиотеку. Тесты SQL/парсера/миграции проверяют независимые ожидаемые результаты, а не повторяют алгоритм реализации.

## Обязательная S3 conformance приёмка

До релиза на реальном Apple Silicon Mac/Docker Desktop запускается **SeaweedFS 4.53 `weed mini`** `linux/arm64` с embedded LevelDB2, credentials и штатным полным `/data` volume; `linux/amd64` проверяется отдельно. В отчёте фиксируются image digests, фактические startup args, файловая система/mount и результат `fs.configure -locationPrefix=/ -fsync=true -apply` **до загрузок**, сохранность global rule и metadata/chunks после restart. Успешный PUT с отсутствующим правилом не соответствует контракту; operational preflight не допускает uploads до исправления. Контейнер storage не публикует S3 port на host и не даёт anonymous access; PostgreSQL не требуется.

Suite использует реальный AWS SDK for Go V2 с точными версиями модулей из `go.mod`/`go.sum`, записанными в отчёте, path-style endpoint и теми же SigV4/checksum настройками, что приложение. Проверяются PUT/GET/HEAD/Delete, ListObjectsV2 с pagination, user metadata/Content-Type, Range/conditional requests и 416 с Content-Range; неверные credentials/подпись и анонимный запрос отвергаются. Для media proxy проверяются GET/HEAD/Range из same-origin browser без прямого S3 URL.

Отдельный streaming fixture передает `UploadPart` из неперематываемого `http.Request.Body` с заранее проверенным `ContentLength`. В отчёте явно фиксируется signing path: `SIGNED-PAYLOAD` с доступным до отправки payload hash либо поддерживаемый SDK режим `UNSIGNED-PAYLOAD`, проверенный с этим SeaweedFS. SigV4 payload signing и S3 body checksum — разные механизмы: использование unsigned payload не разрешает отключить или подменить **явный `ChecksumSHA256`** части. Переданный браузером ожидаемый digest должен реально проверяться storage по полученному body; headers/trailers и автоматические checksum middleware SDK проверяются на конкретной конфигурации, а не выбираются по умолчанию наугад. JSON middleware не читает binary body; SDK не должен буферизовать файл ради seek/hash.

Retry suite доказывает, что SDK не пытается повторно отправить уже прочитанный `Request.Body` как новый полный body. После неоднозначного исхода выполняется существующий reconcile/ListParts-контракт, а повтор browser использует те же связанные bytes/size/SHA256; повтор не получает право изменить binding или создать второй импорт. Для seekable canonical PUT из scratch повтор также использует доказанно те же bytes и candidate. Эти проверки не заменяются успешным PUT маленького seekable buffer.

Multipart fixture включает CreateMultipartUpload с SHA256 algorithm, несколько UploadPart, повторную запись **тех же байтов** того же part number, пагинацию ListParts с проверяемой SHA256, ordered CompleteMultipartUpload, Abort и очистку оставшихся MPU; маленький файл проходит one-part MPU. Проверяются серверные partSize/limits: от 5 MiB до 5 GiB, кроме меньшей last part, максимум 10 000 parts; неверные numbers/размер/порядок/ETag, отсутствующая часть, конфликт generation и запрос после terminal state. Отдельно проверяются 409 для другой binding и negative body-vs-checksum: gateway действительно отклоняет изменённый body, а не просто хранит переданную SHA256. Headers/trailers закреплённого SDK проверяются на этом пути; отсутствие body validation или доказуемого ListParts checksum **блокирует релиз и не обходится отключением checksum**. После каждого успешного Complete обязательны HEAD + полный GET/hash: отсутствующий/неверный объект не принимается по HTTP 200. Timeout/retry suite покрывает Create/UploadPart/ListParts/Complete и S3 PUT с фактически потерянным ответом, late writers после restart, InvalidPart без слепой замены manifest и cancel/delete с late Complete. Это acceptance gate совместимости конкретных версий, а не заявление о полной AWS S3 parity.

## Предлагаемые измеримые цели

Это рекомендуемые начальные acceptance budgets, а не подтверждённые продуктовые требования или результаты замеров прототипа. Исходный ориентир — современный Apple Silicon Mac, локальный SSD, Docker Desktop с выделенными 4 CPU и 4 GiB RAM; фактическую модель Mac, VM limits и версии фиксируют в протоколе. Библиотека: 10 000 items, 2 000 tags, до 100 000 item-tag links, 100 GB primary; эти количества сверх известных 100 GB — синтетический профиль роста.

| Метрика | Начальная цель и способ проверки |
| --- | --- |
| Поиск 24 результатов | p95 server time ≤300 ms для обычных boolean queries; ≤1 s для сложных разрешённых queries, 100 повторов после прогрева |
| Первая полезная выдача | ≤2 s при тёплом запуске в локальном браузере, без ожидания всех изображений; cold start измеряется отдельно |
| Viewer | Не читает весь video до начала показа; seek подтверждён Range запросами, Safari/Chromium tested |
| Streaming upload | Файл 20 GiB при выбранном max проходит native MPU через app proxy без хранения целого тела в RAM; серверный partSize укладывается в S3 limits, рост памяти ограничен постоянным размером буферов |
| Работа во время обработки | Поиск/организация сохраняют согласованные budgets при одном software encode; нет голодания SQL writer |
| RAM | Базовый API idle целевой RSS ≤300 MiB; FFmpeg/браузер и Docker VM считаются отдельно; пик на согласованных fixtures фиксируется и ограничивается настройками |
| Recovery | Небольшая очередь возобновляется ≤30 s после готовности процесса без полного reread 100 GB; глубокая проверка checksum запускается отдельно |
| Диск | Перед новой работой проверяется budget MPU/incoming+canonical candidates+preview+scratch до полного GET/hash, SQLite commit и очистки; при недостатке — 507 без потери единственной сохранной копии |
| Внешний backup/restore | При остановленных app и storage отдельный скрипт сохраняет app data и весь SeaweedFS `/data` с master/filerldb2/volumes, persisted rule/config и secrets; hashes, relations и MPU/incoming восстановлены в чистые volumes; RTO определяется фактическим drill |

Encode не получает универсальный deadline в секундах: длительность зависит от codec, resolution и файла. Профиль FFmpeg должен иметь timeout/no-progress policy, отмену и понятный failure, а заданные budgets проверяются отдельно от throughput кодирования. Если цели не достигаются, сначала профилировать SQL/IO/buffering и ограничить обработку; появление PostgreSQL/Redis само по себе не является критерием production.

Viewer gate не фиксирует YARL как уже проверенную зависимость: на synthetic fixtures отдельно проходят image zoom/rotate в едином встроенном viewer, одинаковое открытие из grid/list/related, secondary content под медиа без правой панели, video controls и точные shortcuts, прекращение playback при смене item, fallback при отказе autoplay, отсутствие poster, focus return и VoiceOver. Controller ARIA и keyboard defaults настраиваются так, чтобы editor не получал viewer shortcuts, а `⌘+`/`⌘−`/`⌘0` сохраняли browser zoom. Все существующие функции обязательны независимо от выбранного пакета; действия/controls v27 обязательны; дополнительные отсутствующие в нём shortcuts остаются backlog. Playwright WebKit не равен shipping Safari, а bundled Chromium может отличаться от Chrome по codecs: Linux CI дополняется проверкой на реальном Mac. Primary links и ограничения кандидата — в [UX-аудите](05-ux-ui-audit.md) и [решении по стеку](09-application-stack-decision.md).

## Миграционная приёмка

Перенос выполняется offline отдельным одноразовым скриптом, с остановленными старым и новым приложениями и read-only источником. Допустимо одновременно хранить полную старую и новую копию: при исходных примерно 100 GB заранее нужно место ещё для полной целевой копии плюс staging/БД/manifest и эксплуатационный резерв. Точный объём и окно недоступности подтверждают scan и rehearsal по [плану миграции](04-migration-and-operations.md); экономия места не должна подменять независимую копию.

Обязательны точные counts по сущностям, equality scalar fields и join sets, сохранение ID либо полная mapping table, per-item primary existence/size/SHA-256, отсутствие молчаливых orphan/duplicate merges, корректные durations, global tag stats, категории и коллекции. Text/Audio/Unknown сохраняют kind и доступные байты; запрет таких новых загрузок на них не распространяется. Перенос 99% файлов недостаточен для заявления о полной миграции. Выявленные исключения имеют ID, причину и отдельное решение пользователя.

Thumbnail можно восстановить, primary — нельзя. Поэтому missing derivative и missing primary имеют разный уровень блокировки. Все `temporary`/`ProcessingFiles` и лишние объекты остаются в архиве/отчёте; старый Failed/Pending не превращается автоматически в новый активный импорт. Legacy-перенос копирует доступные байты без новой conversion и применения правила очистки входа новой загрузки к старому архиву. По завершении отдельно проверить restore внешнего backup отдельным инструментом при остановленном сервисе, а не только чтение новой рабочей библиотеки.

## Условия первого production релиза

- F-01…F-38 и D-01…D-16 покрыты результатами проверок; UI/поведение соответствует принятому v27 и его паспорту. Изменения относительно legacy названы и согласованы; имитация макета не считается production-проверкой.
- Новые загрузки принимают только фото/видео; ready primary сохраняет исходное разрешение. Проверенное сохранение и автоматическое удаление входа проходят как одна операция без дополнительного подтверждения; crash-тест доказывает сохранность, а постоянная библиотека не содержит дополнительного original.
- Подтверждённые правила организации и удаления проверены: одна коллекция, несколько тегов, rename без изменения результата категорий, отдельно подтверждённое окончательное удаление item без корзины.
- Нет неразрешённой потери данных/функций в migration report; все исключения точечные и приняты владельцем.
- На реальном Mac проверены arm64, Safari/Chromium, штатные app/storage volumes, persisted global fsync rule, durability metadata/chunks, restart, sleep и power-loss/recovery; S3 conformance выполнена с точными версиями SeaweedFS/SDK. Проверки immutable part bindings, фактической body checksum validation, late writers/Complete, candidate expected hash/size и D-15 без age-based удаления пройдены. Linux CI и WebKit automation дополняют, но не заменяют эту проверку.
- Два закреплённых образа содержат приложение (production SPA, API, media tools и локальные assets) и SeaweedFS 4.53 `weed mini` с embedded LevelDB2; после pull приложение работает без внешней сети и без PostgreSQL. S3 доступен только приложению во внутренней сети, browser использует same-origin API/media.
- Предоставлены versioned install/update и отказ приложения от записи в несовместимую схему. Миграции собственной схемы проверены отдельно от legacy-переноса.
- Поставлены отдельный одноразовый legacy-скрипт и отдельный backup/restore-скрипт с совместимыми версиями/форматом, проверкой целостности и инструкциями запуска на остановленном сервисе. Они не добавляют migration/export/import/backup/restore API или CLI в основной сервис. Точные команды внешних инструментов документируются после появления реализации.
- Пользователь получил инструкцию по ручному запуску, месту назначения, проверке и хранению внешних backup; ответственность за резервирование остаётся у него. В приложении отсутствуют backup scheduler, кнопки и статус последнего backup.
- Внешний cold backup обоих остановленных контейнеров, включая SQLite, весь SeaweedFS `/data` с master/filerldb2/volumes, partial MPU/incoming и persisted fsync rule/config/secrets, восстановлен в чистые volumes; rollback до и после новых записей описан и испытан.
- Обязательны функциональный паритет, согласованный UI v27 и технические проверки. Приоритет P0/P1 в историческом [UX-аудите](05-ux-ui-audit.md) сам по себе не включает оставшийся backlog; list selection/bulk replace уже принят по D-16 и не может быть исключён как optional.

После релиза можно добавлять новые поисковые фильтры, массовые add/remove и операции через все страницы, дополнительные виды медиа, корзину или новый similarity mode через модули и версионированные контракты. Рабочая библиотека и migration/backup tests остаются ограничениями для каждого изменения.
